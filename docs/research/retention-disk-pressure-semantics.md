# Retention and disk-pressure semantics

- Status: exploratory source review; no retention policy or API selected
- Last reviewed: 2026-10-05
- Baseline: `959565214725760b77e71ae876865dff8444dbc9`
- Scope: retention eligibility, consumer/replay state, physical capacity admission, deletion recovery, and bounded observability
- Related outcome: [Make retention and disk-pressure behavior safe](../backlog.md#make-retention-and-disk-pressure-behavior-safe)
- Related design: [Retention and disk-pressure design](../design/retention-disk-pressure-plan.md)
- Related accepted boundaries: [ADR 0023](../decisions/0023-independent-retained-storage-and-placement.md), [ADR 0024](../decisions/0024-explicit-offset-replay-read.md), [ADR 0026](../decisions/0026-semantic-engine-error-classification.md), [ADR 0028](../decisions/0028-consumer-lag-observation-semantics.md)

This note refines the open policy questions in the linked design. It separates observed Runnel behavior, facts from primary sources, and candidate choices. It does not accept a public policy, API, storage format, or implementation sequence. Future behavior still needs an ADR and the failure evidence listed below.

## Findings

The central design boundary is that **history eligibility, consumer progress, and physical write admission answer different questions**. A size or age rule can make history eligible for removal; consumer and replay semantics decide whether that history may be removed; physical capacity decides whether a new durable mutation can proceed. Treating low disk as implicit permission to expire history would merge those decisions and could silently change an application's replay or acknowledgement outcome.

The [backlog constraints](../backlog.md#make-retention-and-disk-pressure-behavior-safe) require retention and admission to preserve the selected replay and acknowledged-durability guarantees, and forbid silently discarding committed data or accepting a write that cannot be durably completed. The precise policy that satisfies those constraints remains open.

## Observed Runnel behavior at the supplied baseline

These are code observations, not target behavior:

| Area | Observed behavior | Retention consequence |
| --- | --- | --- |
| Local stream log | [`StreamLog::open`](../../crates/runnel-core/src/stream_log.rs#L91-L127) scans records from the beginning to rebuild offsets, sparse indexes, and request IDs. [`append_with_sync`](../../crates/runnel-core/src/stream_log.rs#L190-L232) appends to one file and calls `sync_data` before publishing the new in-memory index. There is no segment manifest, logical retained floor, cleanup worker, or disk-capacity preflight. | Prefix deletion cannot be represented as a safe logical-history change in the current file format. An I/O error after writing begins does not establish that no complete record reached the file. |
| Local consumer state | [`load_consumer_state`](../../crates/runnel-core/src/consumer_state.rs#L120-L142) loads one stream/consumer checkpoint on demand, defaulting a missing checkpoint to offset zero. Durable progress is a contiguous offset plus out-of-order acknowledged offsets. The [`delivery` cache](../../crates/runnel-core/src/delivery_state.rs#L10-L10) is capped at 1,024 states; there is no accepted complete consumer-catalogue or retention query. | A retention implementation cannot use the active cache as proof that it has seen every consumer. `protect` would require a complete bounded source; an incomplete source must not be interpreted as no lagging consumer. |
| Local replay and delivery | [`Broker::replay`](../../crates/runnel-core/src/broker.rs#L294-L307) reads one offset without creating delivery state or changing the normal consumer cursor. Delivery attempts are durable; active delivery leases and tokens are in memory ([`InFlight`](../../crates/runnel-core/src/delivery_state.rs#L20-L29)), and an unacknowledged record can be delivered again after restart ([restart test](../../crates/runnel-core/src/lib.rs#L1552-L1571)). | The current replay read creates no durable pin. Protecting an ongoing replay requires new session state; protecting normal delivery must be defined against the durable cursor and lease semantics rather than inferred from a transient cache. |
| Local acknowledgement | Acknowledgement progress is updated in memory only after [`persist_consumer_event`](../../crates/runnel-core/src/broker.rs#L423-L486) succeeds. Generic `BrokerError::Io` is classified as storage failure with an `Unknown` outcome by [ADR 0026's engine boundary](../../crates/runnel-engine/src/lib.rs#L291-L326). | If an ack write fails under pressure, the broker must not report success. If the write may have persisted, retry safety needs the existing unknown-outcome resolution semantics. |
| Clustered retained state | [`StreamState.messages`](../../crates/runnel-raft/src/state_machine.rs#L144-L170) is a complete `Vec<StoredMessage>`. Snapshots include that state and consumer maps; state-machine journal writes are synced before the apply path continues ([journal append](../../crates/runnel-raft/src/state_machine_store.rs#L450-L463)). | Cluster retention must first be an ordered, durable logical state transition. Per-replica physical cleanup cannot independently determine application-visible eligibility. Current snapshot and recovery costs remain proportional to retained state. |
| Capacity and metrics | The real-server [`sustained_storage_pressure_is_bounded_observable_and_recovers` test](../../crates/runnel-server/tests/admission.rs#L850-L858) exercises synthetic storage-executor saturation, not full filesystems. Local [`storage_bytes`](../../crates/runnel-core/src/broker.rs#L497-L519) counts stream-log file lengths; clustered health counts materialized key and payload lengths in each local group ([cluster health](../../crates/runnel-raft/src/state_machine_store.rs#L651-L677)). Neither is filesystem free space, a full physical inventory, or a cluster-wide deduplicated capacity measure. | Existing storage bytes cannot be used as a disk admission budget. Current tests do not establish behavior for low free space, quota exhaustion, `ENOSPC`, or interrupted data deletion. |

The [retained-storage and placement decision](../decisions/0023-independent-retained-storage-and-placement.md) keeps logical stream identity separate from internal placement and physical segments. [ADR 0028](../decisions/0028-consumer-lag-observation-semantics.md) defines cursor-lag meaning but deliberately does not accept a complete consumer catalogue or runtime query. [ADR 0007](../decisions/0007-snapshot-based-replica-recovery.md) and [ADR 0018](../decisions/0018-safe-replica-recovery-boundary.md) keep consensus-log compaction, retained history, and replacement recovery as separate boundaries.

## Primary and reference evidence

| Source | Sourced fact | Difference that matters to Runnel |
| --- | --- | --- |
| [Apache Kafka 4.2 topic configs](https://kafka.apache.org/42/configuration/topic-configs/) | Time and byte retention operate independently; either can cause old segments to be discarded. Cleanup is segment-granular, and segment roll controls cleanup granularity. The configured time limit is an expectation that consumers read before data expires. | Runnel can borrow separate time/size triggers and segment-granular cleanup, but Kafka's consumer offset does not itself protect retained history. A Runnel lag policy would be an additional contract. |
| [NATS JetStream retention policies](https://docs.nats.io/learn/jetstream/retention-policies) | Limits retention is separate from acknowledgement-driven Interest and WorkQueue retention. A stream's size/age limits remain upper bounds under those acknowledgement policies, so slow consumers can still lose backlog at the cap. WorkQueue ack removes the record for all consumers; Interest waits for all consumers. | Runnel's independent fan-out consumers, shared-consumer cursor, and offset replay do not imply either ack-driven deletion mode. Adopting an ack-based mode or allowing limits to expire unacknowledged work would need explicit semantics, not an incidental consequence of storage pressure. |
| [Redpanda topic properties](https://docs.redpanda.com/streaming/current/reference/properties/topic-properties/) and [local capacity properties](https://docs.redpanda.com/streaming/current/reference/properties/cluster-properties/) | Tiered Storage distinguishes topic-wide retention from local-retention targets. Its local-capacity target can trigger retention when local usage reaches the target; the target is not described as a guarantee that every append fits. | Logical history limits and per-replica physical space are separate controls. Runnel has no tiered copy, but clustered nodes still have independent volumes and may reclaim at different rates after the same logical floor commits. |
| Rosenblum and Ousterhout, [The Design and Implementation of a Log-Structured File System](https://web.stanford.edu/~ouster/cgi-bin/papers/lfs.pdf) | The paper uses segments and a cleaner to maintain large free areas. Cleaning consumes disk bandwidth; its measurements include that cleaning overhead. | Segments make whole-history deletion and bounded cleaning work expressible, but cleanup competes with foreground writes. Runnel must measure reclaim rate, write amplification, and foreground tail latency; the paper does not establish Runnel's segment size or reserve. |
| Linux man-pages: [`statvfs(3)`](https://man7.org/linux/man-pages/man3/statvfs.3.html), [`write(2)`](https://man7.org/linux/man-pages/man2/write.2.html), [`fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html), and [`unlink(2)`](https://man7.org/linux/man-pages/man2/unlink.2.html) | `statvfs` reports filesystem block and inode fields, but its documentation says not all fields need be meaningful on all filesystems. Writes can be partial; `ENOSPC` can be reported by a write or synchronization. `fsync` on a file does not by itself persist the containing directory entry. An unlinked file with open descriptors continues occupying space until they close. | A preflight observation cannot promise later allocation success or immediate reclaimed capacity. Admission needs a bounded race margin and write-stage-aware outcomes; deletion needs file-lifecycle fencing, directory durability where required, and metrics that distinguish logical bytes reclaimed from physical space available. |
| [Prometheus instrumentation guidance](https://prometheus.io/docs/practices/instrumentation/#do-not-overuse-labels) and [ADR 0028](../decisions/0028-consumer-lag-observation-semantics.md) | Prometheus documents the per-label-set resource cost and warns against dimensions whose cardinality grows. ADR 0028 additionally requires consumer freshness, coverage, and retention-expiry to remain distinct. | Default metrics should use bounded state/reason labels. A per-stream or per-consumer list, if later required, belongs in a paginated, bounded inspection surface with explicit completeness and freshness, not identity-labelled time series. |

## Decisions that remain separate

The table describes options and consequences; it does not rank or select them.

| Question | Candidate choices | Consequence and evidence needed |
| --- | --- | --- |
| What makes a record eligible to leave? | **History limits:** time/size alone determine eligibility. **Consumer completion:** all fan-out consumers, or one work-queue consumer, acknowledge first. **Hybrid:** acknowledgement may release data early while time/size remain upper bounds. | History limits preserve replay only inside the configured window. Ack-driven removal changes the role of acknowledgement and independent consumers. Hybrid behavior needs explicit rules for a lagging or newly created consumer. Compare independent fan-out and shared-group tests; do not infer eligibility from a generic ack count. |
| How do lag and replay constrain the logical floor? | **Protect:** consumer and replay cursors fence deletion, so configured limits can be exceeded. **Expire:** explicit policy permits the floor to pass a lagging cursor, and the client receives unavailable history. **Bounded grace:** active delivery or replay leases delay expiry for a documented interval. | A complete durable cursor inventory is required to implement protection. Under expiry, tests must decide what happens to unacknowledged delivery, out-of-order group acknowledgements, stale tokens, and replay reads racing the floor advance. Consumer inactivity/deletion cannot silently erase a pin. |
| Which rule wins among age, size, lag, and reserve? | Time and size can be independent candidate triggers (Kafka precedent); lag can veto candidates (protect), or an explicit expiry choice can remove history; a reserve can be treated as a hard admission boundary. A different option is pressure-driven expiry. | Pressure-driven expiry is easy to confuse with the configured replay promise. The backlog requires preserving the selected guarantee and forbids silent discard, so any pressure-driven change would need an explicit user-visible policy transition. Decide whether age/size are hard caps or eligibility targets when consumers protect history, and report overage when candidates are fenced. |
| What does `max_bytes` count? | Logical payload/key bytes; encoded record bytes; or separate logical and physical accounting. | Encoded bytes are closer to segment deletion but change with framing/compression. Per-stream bytes do not bound journals, checkpoints, snapshots, temporary manifests, other files, or replica copies. Define the unit before accepting limits or comparing local and clustered metrics. |
| How does admission behave near full capacity? | **Preflight only:** reject before append based on observed capacity and reserved headroom. **Preflight plus reactive handling:** use preflight for ordinary admission but handle actual partial write, sync, metadata, quota, and directory errors. **Reservation/accounting:** reserve capacity against concurrent broker operations, reducing but not eliminating external races. | Filesystem statistics are snapshots. `ENOSPC` or quota errors may arrive after append or at sync, so outcomes depend on whether a mutation could have reached the durable point. Test appends, batched partial outcomes, acks, manifest writes, and snapshot/journal writes separately. A provider failure also needs an explicit conservative behavior. |
| What happens if a clustered replica is full? | Stop local writes; continue while a selected quorum can durably commit; or enter a degraded state that blocks new writes. | The current engine has no selectable durability profile or capacity-aware quorum policy. One replica's physical cleanup is local; the committed logical floor is replicated. Test configured memberships, full leader/follower cases, loss of writable quorum, leadership change, restart, and replacement without claiming arbitrary three-node tolerance. |
| In which order are floor publication and deletion performed? | **Floor first:** durably publish the logical boundary, then unlink unreferenced segments and retry orphan cleanup. **Delete first:** reclaim first, then publish the floor. **Staged generation:** prepare immutable metadata, publish a generation, then remove only unreferenced files. | Deleting data still referenced by the authoritative manifest can make recovery fail or resurrect an impossible range. Floor-first makes cleanup interruption an over-retention problem, but can make history unavailable before bytes are reclaimed and requires enough reserved space to persist the new manifest. Validate every crash point and actual directory-sync behavior. |
| What can an operator observe within a bounded budget? | Fixed-cardinality aggregate metrics; bounded per-stream pages; cached/sampled detail with freshness/coverage; or a complete but potentially linear inspection operation. | `storage_bytes` today has different local and clustered meanings. A complete lag query needs a bounded source and coverage per ADR 0028. Measure scrape cost under many streams and consumers; no partial inventory may be represented as complete or as zero. |

## Inferences and candidate boundaries

The following are design inferences from the accepted backlog constraints and sources, not new accepted policy:

- Treat retention limits as a logical eligibility rule and free-space admission as a physical-safety rule, with an explicit interaction rather than one silently overriding the other.
- Preserve the distinction between an acknowledged cursor, an out-of-order acknowledgement, an active lease, and a replay session. They imply different retention rights; `H - C` is not an exact count of reclaimable records.
- If a complete cursor catalogue does not fit a bounded query, `protect` cannot safely assume that unobserved consumers are absent. The design needs a durable summary/catalogue or an explicit incomplete-coverage result.
- Treat capacity preflight as advisory. Keep a maximum legal mutation and bounded concurrency inside the reserve calculation, but still classify write, sync, directory, and quota failures by durable stage. A post-write storage failure remains `Unknown` unless the implementation proves the mutation did not apply.
- Commit one logical floor and let each cluster replica reclaim locally only after applying that committed state. A node with orphaned bytes is physically pressured but must not invent a different visible history.
- Separate operator status by source and scope: logical retained/reclaimable bytes, physical free/available space, reserve/headroom, cleanup backlog, and consumer/replay constraints are not interchangeable measurements.

## Evidence required before a policy decision

The design plan's broader matrix remains useful. This source review identifies the minimum evidence needed to resolve its policy branches:

1. Demonstrate how the selected history policy treats a fully caught-up consumer, a durable lagging consumer, an out-of-order group acknowledgement, an unacknowledged delivery, a replay read, and a replay session. Test `history_unavailable` and acknowledgement fencing at the public protocol.
2. Inject failure before, during, and after record append/sync, consumer-state persistence, manifest publication, directory sync, unlink, state-machine journal sync, and snapshot persistence. Reopen the real process and classify each result as committed, rejected/retryable, or unknown using stable request identity where available.
3. Exercise a capacity-provider test boundary and a real constrained filesystem or quota. Change free space between preflight and write. Include free blocks, inodes, metadata, temporary files, concurrent maximum-sized operations, local and follower-full clustered cases, and confirm that metrics remain available.
4. Measure cleanup throughput and backlog under steady publish, including protected lag, segment-granularity overage, and deletion failure. Report foreground p99/p99.9, recovery time, storage bytes, bytes reclaimed, and whether unlinked-but-open files delay physical capacity recovery.
5. Bound consumer/replay inventory work and metrics scrape time under many streams and consumers. Report freshness, source revision, and coverage independently; do not claim a global aggregate from node-local replicas.

These are evidence gates for a future design/ADR and implementation. This note does not recommend enabling finite retention, selecting `protect` or `expire`, choosing a reserve formula, changing health/readiness, or adding a new public operation.
