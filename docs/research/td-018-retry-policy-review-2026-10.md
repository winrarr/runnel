## Finding

The application-aware retry proposal remains supported by current source and the current accepted decision. ADR 0027 covers durable consumer-scoped acknowledgement timeouts and attempt limits, with policy snapshots pinned on first assignment. The shared [`assert_consumer_policy_configuration_contract`](../../crates/runnel-test-support/src/lib.rs#L255) checks fallback, consumer isolation, idempotent repeats, version advancement, and rejection of a zero attempt limit; [`local_engine_implements_consumer_policy_configuration_contract`](../../crates/runnel-core/tests/engine_contract.rs#L43), [`single_node_raft_implements_consumer_policy_configuration_contract`](../../crates/runnel-raft/src/lib.rs#L1012), and [`persistent_raft_implements_consumer_policy_configuration_contract`](../../crates/runnel-raft/src/lib.rs#L1043) run it. The public [CLI documentation](../../README.md) exposes `configure-consumer` and `inspect-consumer` for one stream/consumer pair: zero timeout is allowed, its maximum is seven days, a specified attempt limit must be positive, and an omitted limit means `null` rather than the broker-wide fallback. The real-process smoke script runs [`configure-consumer`](../../scripts/smoke.sh#L159), then after broker restart runs [`inspect-consumer`](../../scripts/smoke.sh#L171) and checks the configured values and version with [`assert_consumer_policy`](../../scripts/smoke.sh#L95). This verifies durable policy configuration across a real restart; it does not establish semantics for a future scheduled retry delay. Backoff, explicit failure dispositions, public dead-letter provenance, and redrive remain proposals. This review refreshes reference evidence and names unresolved implementation gates; it does not accept a new policy or prescribe the proposal's example API or storage shape.

## Current Runnel boundary

At this baseline, local consumer journals persist attempt counts and the policy snapshot before returning a delivery, but active leases use process-local `Instant` state. A restart retains attempts and makes an unacknowledged record eligible immediately. The clustered engine replicates in-flight deadlines and attempt state with the consumer transition; deadlines use leader-observed wall clock values and a persisted observation floor, not a bound on clock skew or forward jumps. Both engines evaluate expiry on later operations rather than a background timer. These facts are visible in [`ConsumerState`](../../crates/runnel-core/src/consumer_state.rs), [`DeliveryState`](../../crates/runnel-core/src/delivery_state.rs), [`Broker::poll_group`](../../crates/runnel-core/src/broker.rs), and [`apply_group_poll`](../../crates/runnel-raft/src/delivery.rs); the clock limits remain tracked in [TD-020](../tech-debt.md#td-020-clustered-delivery-leases-use-absolute-wall-clock-deadlines).

An exhausted attempt budget currently moves the key and payload to the derived dead-letter stream. Locally, the target append precedes source progress and uses an internal move identity for reconciliation; [`dead_letter_retry_reuses_move_identity_without_appending`](../../crates/runnel-core/src/lib.rs#L1143) and [`dead_letter_move_reconciles_target_after_restart`](../../crates/runnel-core/src/lib.rs#L1179) cover retries of that broker-generated ID after repeated calls and reopen. The supplied baseline adds public same-content collision coverage: [`dead_letter_move_same_content_public_id_reconciles_after_restart`](../../crates/runnel-core/src/lib.rs#L1481) publishes the matching key and payload under the exact derived move ID, injects a source-ack persistence error, then reopens and verifies source progress completes without appending another target record. The real-server test [`network_protocol_reconciles_same_content_public_dead_letter_id_after_restart`](../../crates/runnel-server/tests/server_smoke.rs#L1053) exercises the matching public ID over the wire and confirms one target record and completed source progress after restart. Mismatching content is covered separately by [`dead_letter_move_content_mismatch_is_storage_error_without_acknowledgement`](../../crates/runnel-core/src/lib.rs#L1442) and [`network_protocol_preserves_public_record_on_dead_letter_move_id_collision_after_restart`](../../crates/runnel-server/tests/server_smoke.rs#L923).

This evidence closes the same-content behavior gap, but not the [TD-029](../tech-debt.md#td-029-public-request-ids-can-collide-with-local-dead-letter-move-ids) identity question. The local request-ID index treats a public record with the same ID, key, and payload as the generated move; the tests establish the current reconciliation outcome, not proof that the matching record originated from a move. The companion [TD-029 identity research](td-029-dead-letter-identity-contract.md) compares content matching, reserved prefixes, typed identities, and recovery journals. Its typed-identity direction is an exploratory recommendation, conditional on an explicit RNL3 upgrade policy; this review leaves identity and provenance semantics unresolved. In the cluster, the copy and source progress share one replicated data-group transition. Neither public path exposes source provenance or offers a redrive or explicit retry/terminal disposition. The exact local and clustered limits, including the local append/checkpoint boundary, are recorded in [the recovery design](../design/dead-letter-recovery.md).

## Primary-source comparison

The project documentation references below were checked on 2026-10-02 against current official sources. The Raft paper is included for the replicated-state-machine invariant. The transfer column is an inference for Runnel; it does not claim equivalent semantics.

| Reference | What its current documentation establishes | Relevance and non-transfer to Runnel |
| --- | --- | --- |
| [NATS JetStream acknowledgements and redelivery](https://docs.nats.io/learn/jetstream/acknowledgment) | `AckWait` is the processing-response deadline; `in-progress` resets it. A delayed `nak` schedules one retry, while consumer `BackOff` shapes timeout redelivery, replaces `AckWait`, and does not delay `nak`. `MaxDeliver` can stop delivery without a built-in DLQ; advisories report exhaustion. | This is evidence that lease expiry and an explicit failure retry can need distinct timing controls. Its backoff/lease coupling is a caution for Runnel's proposed separate fields. NATS `term` advances that consumer's acknowledgement state and leaves stream retention to its retention policy; that is not automatically equivalent to Runnel's proposed `hold` or copy-then-advance dead-letter action. |
| [Apache Pulsar 4.2 messaging](https://pulsar.apache.org/docs/4.2.x/concepts-messaging/) | The retry-letter-topic path stores retry count and delay as message properties; the docs warn that ordinary negative-ack redelivery counters can reset, and identify `reconsumeLater` with retry enabled as the reliable path to a configured retry limit. The retry-topic feature is implemented by consumers. | This supports durable retry accounting and explicit distinction between ordinary redelivery and scheduled retry. It does not require Runnel to move records into per-consumer retry topics: Runnel's shared stream, consumer offsets, key gates, retention, and state ownership differ, and a retry topic would create another record/delivery identity. |
| [Raft replicated-state-machine paper](https://raft.github.io/raft.pdf) | Replicas apply the same ordered log commands; deterministic state machines compute the same state and outputs. | For Runnel, any selected retry deadline or jitter value that changes apply state must derive from committed inputs/state or be included in the committed command. Replica-local random sampling would violate that requirement. This establishes deterministic application, not a bound on wall-clock accuracy or scheduling availability. |
| [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues) and [dead-letter exchanges](https://www.rabbitmq.com/docs/dlx) | The current quorum-queue docs distinguish acquisition count from unsuccessful delivery count; timeouts and connection loss affect those counters differently from explicit returns. At-least-once dead-lettering retains source messages until targets confirm and can produce target duplicates on retries. Pending messages consume source resources; internal prefetch limits in-memory bodies, while queue length limits are needed to bound retained backlog. | Attempt definitions must be explicit: Runnel currently counts committed assignments, so RabbitMQ's failed-delivery count is not a drop-in definition. The resource and duplicate trade-off supports making blocked-target behavior and bounds explicit, but RabbitMQ queue removal, confirms, routing, and queue limits do not establish Runnel's append/checkpoint or same-group Raft guarantees. |
| [Amazon SQS receive API](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_ReceiveMessage.html), [DLQ policy](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html), and [redrive task API](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_StartMessageMoveTask.html) | Receive results can expose an approximate receive count and the DLQ source ARN. Redrive is an asynchronous move task, permits one active task per queue, and supports a configured rate up to 500 messages per second. | These are useful precedents for origin metadata and operator-controlled, rate-bounded redrive. SQS queue/ARN identity, visibility timeout, retention, and queue movement do not transfer directly to Runnel's `(stream, consumer, offset)` identity, independent fan-out consumers, or provisional redrive outcome contract. |

## Open evidence gates

The existing proposal already identifies the following as unaccepted work. This review confirms that the implementation and current references still support those boundaries; it does not find a new runtime requirement.

| Area | Supported proposal direction | Evidence still needed before implementation is accepted |
| --- | --- | --- |
| Processing lease and retry delay | Keep the active acknowledgement lease distinct from a scheduled retry delay. A timeout means no answer was observed; an explicit retry is a known failure. | Define which events schedule a retry, when the active lease ends, whether active leases survive restart, the due-time clock/error and no-quorum behavior, and key/unkeyed ordering while waiting. The current clustered wall-clock model does not establish a real-time deadline bound. |
| Deterministic backoff | Bound and saturate fixed/exponential delay, derive any jitter deterministically for replicated application, and persist the selected `retry_not_before` value. | Freeze a versioned calculation and stable source identity, add deterministic vectors and boundary tests, show that the identity-derived schedule spreads independent records, and test replay/failover without recomputing a different deadline. The [Raft replicated-state-machine model](https://raft.github.io/raft.pdf) requires identical ordered commands and deterministic application; for Runnel, replica-local random sampling must therefore be replaced by committed inputs/state or a committed seed/delay. |
| Durable retry state | Keep attempts and policy with the durable consumer/record lifecycle; do not count polls or transient shared members as attempts. | Add restart, snapshot/journal replay, leader-transfer, uncertain-response, policy-update, schedule expiry, and bounded state/compaction coverage for the new deadline. The current durable attempt count is not evidence that a future schedule is already durable. |
| Provenance | Report source identity, attempts, policy version, terminal reason, and whether the record was redriven, without inferring missing history. | Define stream-incarnation identity, bounded lineage and format/version behavior, legacy records as incomplete, and consistent local/clustered metadata. The local internal move ID is private reconciliation state; the clustered same-group path has no matching ID field. |
| Terminal disposition | Make retry, hold, and dead-letter choices explicit; never hide data loss behind attempt exhaustion. | Define whether a permanent-failure signal is distinct from retry exhaustion, the progress/key-blocking semantics of `hold`, target failures, and bounded observability. NATS `term` is consumer completion/skip behavior, not a Runnel dead-letter operation. |
| Redrive | Make redrive deliberate and duplicate-safe with a stable intent identity, a new destination offset, destination-policy attempt 1, and bounded lineage. | Cover same/cross-group movement, conflicting or uncertain target writes, retry after restart, retention crossing, rate/concurrency limits, and authorization. SQS supplies an operator task and rate cap, not a transaction with Runnel's source consumer acknowledgement. |

## Disposition

Backoff, provenance, terminal handling, and redrive are reasonably actionable follow-up outcomes, but they are already tracked by TD-018 and its linked backlog item. The local-versus-clustered move boundary and identity conflict are separately tracked by TD-017 and TD-029; clustered lease-time assumptions are tracked by TD-020. No backlog, tech-debt, ADR, or design edit is warranted from this source refresh. Keep the proposal exploratory until a specific runtime slice has a reviewed semantic boundary and its own evidence plan.

This is documentation-only. Runtime tests do not apply because no executable behavior, protocol, storage, or accepted decision changed. Documentation verification is `git diff --check` plus validation that the new internal links resolve; the linked implementation tests remain the evidence for the current behavior, not for any proposed future schedule or redrive path.
