# Cluster peer transport security

**Status:** Source-backed research; no accepted runtime contract. **Reviewed:** 2026-10-05. **Baseline:** `09ed198de1c55333645e99d2e8e38872673fba2a`.

This note covers node-to-node traffic in Runnel's current static three-node Raft deployment: Raft RPCs, forwarded broker operations, and data-group setup. The [single-node client and operations security proposal](../design/single-node-security.md) explicitly excludes peer authentication and encryption. This note is a separate research outcome for [cluster operability](../backlog.md#make-the-clustered-deployment-operable); it does not define public-client security, implement transport changes, choose a crate or API, accept a security policy, or add an ADR.

The labels below distinguish **observed Runnel behavior** (code and deployment files at the supplied baseline), **reference facts** (external primary sources), **inference** (implications derived from those facts), **candidates** (options to evaluate), and **open choices** (questions requiring later evidence and a decision).

## Observed Runnel behavior

- The server binds the peer listener as a plain Tokio `TcpListener`. The peer handler accepts connections and reads frames directly; there is no TLS handshake, authentication step, or connection-to-node identity check before handling requests ([server bootstrap](../../crates/runnel-server/src/bootstrap.rs#L101-L128), [inbound handler](../../crates/runnel-raft/src/network/inbound.rs#L13-L50)).
- Peer frames are a big-endian 32-bit length followed by JSON. The current frame body limit is 64 MiB. `PeerRequest` has Raft append, vote, and snapshot operations, plus `Forward` and `EnsureDataGroup`; its wire shape has no version or identity envelope ([framing](../../crates/runnel-raft/src/network/framing.rs#L9-L48), [request types](../../crates/runnel-raft/src/network.rs#L15-L87)).
- After decoding, the inbound handler passes Raft calls to the selected group and forwarded operations to the local group manager. The forwarding enum covers create, publish, poll, replay, acknowledgement, consumer configuration and inspection, grouped delivery, and data-stream initialization ([inbound dispatch](../../crates/runnel-raft/src/network/inbound.rs#L50-L101), [forwarding operations](../../crates/runnel-raft/src/network.rs#L40-L125)). This listener therefore exposes both consensus and broad internal broker operations to any network client that can reach it.
- Accepted sockets each spawn a task. This handler has no peer-specific admission semaphore or frame-read deadline; a frame is bounded in size, but a reachable caller can still open connections, hold them without completing a frame, or make the server allocate up to the frame limit per request. The ordinary client protocol's admission controls are not applied in this path ([inbound handler](../../crates/runnel-raft/src/network/inbound.rs#L13-L49), [frame reader](../../crates/runnel-raft/src/network/framing.rs#L31-L48)). This is an observed resource boundary, not a demonstrated exploit or a quantified denial-of-service result.
- Outbound peer communication also uses plain `TcpStream`s. Runnel connects to the address in the Raft node metadata or configured peer map and reuses connections along the replication and compatibility-pool paths ([outbound adapter](../../crates/runnel-raft/src/network/outbound.rs#L42-L88), [connection setup](../../crates/runnel-raft/src/network/outbound.rs#L130-L163)). Compatibility sockets age out lazily after 30 seconds of idleness; current code has no certificate loading or hot-reload lifecycle ([pool expiry](../../crates/runnel-raft/src/network/outbound.rs#L26-L40), [checkout expiry](../../crates/runnel-raft/src/network/outbound.rs#L430-L450)).
- Cluster membership is supplied as static `node-id=address` arguments and becomes Raft `BasicNode` address metadata ([argument parsing](../../crates/runnel-server/src/bootstrap.rs#L61-L69), [peer parsing](../../crates/runnel-server/src/bootstrap.rs#L158-L178), [initial membership](../../crates/runnel-raft/src/engine.rs#L931-L943)). Persisted `cluster_name` and `node_id` checks reject a local data directory configured for another identity; they do not authenticate remote sockets ([storage identity check](../../crates/runnel-raft/src/engine.rs#L40-L103)).
- The illustrative Kubernetes deployment binds peer port 7000 to all pod interfaces and includes it in a headless Service. The manifest has no NetworkPolicy, TLS, authentication, or credential rotation and describes itself as development-only ([manifest](../../deploy/kubernetes/runnel.yaml#L1-L5), [peer Service](../../deploy/kubernetes/runnel.yaml#L23-L42), [peer bind and static addresses](../../deploy/kubernetes/runnel.yaml#L92-L112)). Its documentation requires a trusted development network and says the static peer list is independent of Kubernetes membership management ([deployment security assumptions](../../deploy/kubernetes/README.md#resources-and-security-assumptions), [peer membership](../../deploy/kubernetes/README.md#control-plane-and-peer-membership)).
- The existing cluster design uses three static voters and a custom Runnel-owned network adapter. OpenRaft's pinned `RaftNetworkFactory` and `RaftNetwork` interfaces leave connection creation and RPC transport to that adapter ([ADR 0004](../decisions/0004-multi-raft-first-distributed-engine.md), [OpenRaft 0.9.25 network factory](https://docs.rs/openraft/0.9.25/openraft/network/trait.RaftNetworkFactory.html), [network interface](https://docs.rs/openraft/0.9.25/openraft/network/trait.RaftNetwork.html)). This is an extension point, not built-in peer security.

## Threat model and limits

Treat every path to peer port 7000 as untrusted unless a later deployment and transport design proves otherwise. Relevant actors include a process in another pod or network segment, an on-path observer or modifier, an accidentally exposed service, a stale or misconfigured process, and an operator who distributes the wrong credentials. Assets include message payloads and keys replicated in append or snapshot traffic, consumer state, Raft membership and leadership progress, peer credentials, and availability.

**Inference:** A reachable unauthenticated caller can submit any syntactically valid peer request, including requests that invoke Raft methods or internal broker operations. The exact effects depend on Raft and state-machine preconditions; this source inspection is not a penetration test and does not establish a specific forged-message exploit. Plain TCP offers no cryptographic confidentiality or integrity for peer frames. Malformed frames and connection floods also consume parsing, task, socket, and memory resources before any cluster identity is established.

Raft's primary reference describes crashes, partitions, retries, and recovery; it does not claim resistance to a malicious member that can impersonate another voter or send adversarial RPCs ([Raft paper](https://raft.github.io/raft.pdf)). Authentication can keep an outside process from entering this trusted-member boundary. It cannot make a compromised, authorized node benign, protect data at rest, prevent volumetric network denial of service, or replace correct Raft membership and recovery.

The peer boundary is distinct from the public client listener and HTTP operations endpoints. Securing one listener would not secure the others. Network-level pod isolation can reduce who reaches port 7000, but does not itself encrypt or cryptographically identify an individual peer. A valid peer identity also does not define authorization inside `Forward`: all current static members can reach the same broad peer request set.

## Candidate security boundaries

The following are candidates for a later decision, not accepted requirements or configuration instructions.

1. **Static, operator-managed mutual TLS.** Give each configured node a distinct private key and certificate; have both endpoints validate the chain and the expected peer identity. Map the authenticated certificate identity to the static peer/node ID and intended cluster, rather than accepting every certificate signed by a broad organizational CA. This fits the current three-member static topology and existing transport adapter. A shared cluster CA is operationally simple but gives every certificate it issues potential peer authority unless node identity is separately checked; per-node pinning limits the trusted set but makes replacement and trust rotation more manual.
2. **Managed workload identity with mutual TLS.** A SPIFFE/SPIRE identity can issue short-lived per-workload certificates and update trust bundles. It may fit later deployments that already depend on this control plane. It adds agent availability, workload attestation rules, identity naming, and synchronized configuration behavior; none exists in the current manifest.
3. **NetworkPolicy plus transport security.** Restrict ingress and egress for peer traffic to cluster member pods, and separately secure the socket. Network policy alone is an exposure-reduction measure because its documented boundary is network-flow filtering, not cryptographic peer identity or confidentiality.
4. **One-way server-authenticated TLS.** This can let outbound nodes verify the remote server and encrypt the stream, but the accepting node does not thereby know which configured member connected. It is insufficient by itself for an exposed peer request endpoint.
5. **Automatic self-signed TLS or a shared token/HMAC.** etcd documents self-signed peer TLS as encryption without peer identity authentication. A custom token or frame MAC could authenticate possession of a secret, but would not provide confidentiality without a secure channel and would leave replay, key distribution, rotation, and protocol design to Runnel. Neither is equivalent to a defined per-node trust policy.

For any certificate option, a later design should specify certificate purpose and identity matching, expected membership, cluster scoping, key custody, trust-bundle distribution, certificate expiry and revocation, and behavior when credentials are absent or invalid. Node identity from a certificate must not silently replace Raft's configured membership or the persisted storage identity checks.

## Framing, versioning, and mixed deployments

TLS version negotiation is not peer-RPC compatibility negotiation. The TLS RFC explicitly leaves application protocol startup and certificate interpretation to the protocol designer. The current `PeerRequest` has no version preface or capability field, and the deployment docs say peer/protocol compatibility and mixed-binary operation are undefined.

**Candidate:** establish TLS before reading any Runnel frame; require both peers to authenticate; then either require an exact supported peer-protocol version or negotiate an explicitly defined compatibility range. If application-level negotiation is needed, bind it to the authenticated channel and validate the cluster and node identity before admitting RPCs. Do not trust a claimed node ID in an unauthenticated frame, treat a TLS protocol version as the Runnel peer version, or fall back to plaintext after a handshake or version failure. Disable TLS 1.3 early application data (0-RTT) unless a later protocol profile establishes replay safety for every allowed RPC: Runnel's peer variants include state-changing operations, and the current protocol has no 0-RTT rules. TLS 1.3 resumption without early application data remains a performance candidate to measure ([RFC 9846 replay guidance](https://www.rfc-editor.org/info/rfc9846/)).

No current source proves that mixed secured and unsecured peers can form a safe rollout, nor that a changed peer frame can interoperate with older binaries. etcd's stepwise peer-URL migration is evidence that security rollout may require a coordinated sequence, not evidence that Runnel's fixed membership and `OnDelete` StatefulSet can safely perform one. A supported rotation or upgrade flow needs explicit mixed-state rules and a real three-process validation.

## Rotation, failure, and operational boundaries

- Keep peer keys and trust material separate from public-client credentials and broker data. Supply them at runtime through an operator-controlled secret source; do not embed them in images, manifests, arguments, or persistent data. Kubernetes Secret use still requires access control and at-rest protection.
- For a file-managed certificate candidate, evaluate trust overlap: distribute a trust bundle that accepts both old and new issuers, change one node at a time, verify authenticated links and replication, then remove the old issuer only after all peers have moved. A three-voter cluster requires a working majority of two; simultaneous restarts or a trust error affecting two nodes removes write progress. This sequence is a proposed test scenario, not a supported Runnel procedure.
- Certificate replacement does not inherently revoke an already established TLS connection. Runnel reuses outbound sockets and has no certificate reload/forced peer reconnection behavior today. A design must specify restart versus reload, maximum connection age or explicit closure, and how revocation reaches active connections. Inbound peer connections currently remain in their request loop until the socket closes or errors.
- Missing files, unreadable keys, mismatched certificates, expired certificates, an untrusted issuer, an unexpected identity, and incompatible peer versions should fail closed before any frame reaches a group manager. Diagnostics should distinguish handshake, identity, and version failures from network reachability while avoiding secret material and high-cardinality untrusted identifiers in logs.
- A TLS or identity failure is also a consensus availability failure: the affected RPC is unreachable to Raft. Error reporting and metrics should allow an operator to separate authentication/configuration faults from ordinary packet loss, storage failure, and a real member outage. Unauthenticated connection floods still need bounded handshake work, sockets, concurrent tasks, read time, and memory; TLS does not prevent resource exhaustion by itself.
- Do not treat `/health/ready` as a peer-security or all-groups health proof. The current deployment readiness check establishes metadata initialization and an elected leader, not authenticated connectivity for every group, every configured peer, or bounded replication lag ([deployment readiness semantics](../../deploy/kubernetes/README.md#health-and-traffic-routing)).

## Evidence required before choosing or implementing

Security correctness should be tested on a real three-process cluster in addition to focused TLS and framing tests. Candidate acceptance evidence should include:

- All configured members authenticate each other and establish protected peer connections; a process with no certificate, a certificate from the wrong CA, an expired certificate, a valid but wrong node identity, a wrong-cluster identity, an unconfigured member, or plaintext traffic is rejected before Raft or forwarding dispatch. There is no plaintext downgrade path.
- Wrong or missing files, invalid key/certificate pairs, trust-bundle parse failures, identity mismatch, handshake timeout, peer-version mismatch, and certificate expiry have explicit startup or connection outcomes. The broker must not silently enter an insecure mode.
- An attempted rotation covers old/new trust overlap, one member unavailable at a time, replacement of established sockets, restart/rejoin, and confirmation that commits stop when fewer than two voters can authenticate. Test both the documented Kubernetes deployment boundary and a process-level cluster without Kubernetes assumptions.
- An unauthenticated slow reader, a burst of handshakes, malformed frames, and a maximum-size frame remain within explicit connection, CPU, memory, and timeout bounds. Confirm that authorization occurs before frame parsing and manager dispatch if the chosen transport can enforce that boundary.
- Compare an unsecured diagnostic baseline and the candidate under the same three-node workload and hardware. Cover small and large published payloads, follower forwarding, ordinary append/heartbeat traffic, connection churn, initial recovery, and snapshot transfer. Record per-node CPU, resident memory, active sockets, handshake rate and duration, publish throughput, durable-commit p50/p99/p99.9 latency, replication lag, and snapshot throughput. Repeat measurements with host and storage contention controlled; do not infer performance from the cryptographic algorithm alone.

The payload and concurrency matrix should reuse documented Runnel workloads, then add representative frame sizes (for example 100 B, 1 KiB, 64 KiB, and 1 MiB) and both warm persistent connections and forced reconnects. These are proposed evidence points, not product limits. Persistent sockets can amortize handshake work, while per-connection TLS state and record buffers add memory and file-descriptor pressure. The current adapter keeps direct replication connections per OpenRaft client/group and also uses a bounded compatibility pool ([transport ownership evidence](td-012-peer-transport-ownership.md)); many stream groups may therefore multiply live secure connections. Record encryption adds per-byte CPU and may affect copies and latency depending on the selected TLS implementation. TLS cost is likely concentrated differently between connection setup, repeated frame protection, and large snapshot traffic; per-node CPU, memory, copying, and tail-latency effects remain hypotheses until measured.

## Disposition and open choices

Near-term implementation is feasible for the fixed three-node deployment: static peers already have configured addresses and node IDs, and OpenRaft exposes a Runnel-owned transport seam. A peer-only TLS/mTLS adapter can be evaluated without changing the public client contract or consensus state model. However, safe rollout, identity-to-node mapping, secret lifecycle, authentication-failure diagnostics, and resource bounds are not currently defined or tested. Treat peer security as an active gap in the existing clustered-operability outcome, and require a decision before calling the deployment secure or production-operable.

Open choices include certificate identity format and matching rules; cluster-scoped CA, pinned peer identities, or workload identity; certificate and trust rotation/reload behavior; revocation and expiry policy; which TLS versions and peer protocol versions to support; exact protocol-version negotiation versus strict version matching; connection-age and handshake/resource limits; metrics and operator diagnostics; and whether the development manifest should include a NetworkPolicy as defense in depth.

The existing backlog already requires authentication, TLS, runtime-supplied credentials, rotation, and repeatable security tests for the cluster. The backlog update links this research and records the current peer-authentication gap; no new backlog item or tech-debt entry is needed. No ADR is added because no option has been accepted. The single-node security proposal, public client security, and runtime code remain unchanged.
