# Raft log persistence contract

- Status: accepted behavior; v3 runtime implemented, clustered and cost gates open under [ADR 0040](../decisions/0040-bounded-raft-log-persistence.md)
- Scope: [TD-026](../tech-debt.md#td-026-raft-log-persistence-rewrites-retained-entries) and [clustered commit-cost backlog outcome](../backlog.md#keep-clustered-commit-cost-predictable-as-consensus-history-grows)
- Related boundaries: [ADR 0037](../decisions/0037-offline-side-by-side-storage-upgrades.md), [ADR 0007](../decisions/0007-snapshot-based-replica-recovery.md), [OpenRaft 0.9.25 `RaftLogStorage`](https://docs.rs/openraft/0.9.25/openraft/storage/trait.RaftLogStorage.html)

## Goal and evidence boundary

The current `LogStore` serializes the entire retained `BTreeMap` and atomically replaces `raft-log.json` for append, vote, committed-index, truncate, and purge operations. At 4,096 retained 1-KiB entries, an isolated append/commit pair took 75.8 ms median and serialized 35.2 MB, compared with 32.6 ms and 8.8 KiB with no retained entries. This demonstrates a history-proportional local rewrite mechanism. It does not establish the end-to-end cluster latency, physical filesystem/device writes, a supported workload limit, or the performance of a replacement.

## Selected persistence behavior

The replacement is the current version-3 Raft-log artifact family with two parts:

1. A checksummed, append-only sequence of bounded entry segments. Each segment stores consecutive OpenRaft entries as individually framed records. A segment rolls at a fixed implementation-defined byte/record target. A single entry that fits the existing accepted Raft-entry envelope may occupy its own segment even when it exceeds the target; this decision adds no public payload limit.
2. A small atomically replaced control-state record containing only the latest vote, committed log ID, purge floor, and the minimal generation/truncation boundary needed to interpret the segments. Its size is independent of retained log length and number of prior updates. It contains no entry map or history-sized segment catalog.

The Raft store continues to serialize all persistent writes for a group in one order, including vote writes and entry writes. An append serializes the supplied entries once, writes only those records plus fixed framing and any segment-roll header, and synchronizes every touched segment before reporting its flush callback as successful. Creating a segment also durably publishes its directory entry before success. The method may return after entries become readable and before the callback completes, as OpenRaft permits; the callback remains the durability boundary. This decision adds no group-commit delay and does not weaken the existing durability mode. A vote or committed-index update durably replaces only the bounded control state before returning. In-memory indexing may still scale with retained entries; the accepted bound concerns persistent work, while memory and CPU costs remain separate.

For a fixed appended batch, entry bytes serialized and submitted to storage must not increase with older retained entries or segment count. Work may scale with the new batch bytes, the bounded number of segments that batch rolls, the fixed control record for a control-state operation, and the existing in-memory index operation. No append or committed-index update may serialize, copy, or rewrite previously retained entry payloads.

### Ordering and failure semantics

- `append` makes its supplied entries readable through the log reader when the method returns, as required by OpenRaft. Its flush callback reports success only after the corresponding complete batch is durable. All writes, including `save_vote`, remain serialized so a later vote or log write cannot complete ahead of an earlier one.
- Framing must distinguish a complete durable batch from an interrupted trailing batch. A partial final batch with no valid completion marker can be discarded on recovery; a checksum or structural failure inside a completed batch or sealed segment fails closed. Recovery never skips a record to invent a contiguous log.
- A failed write or sync does not prove no effect. The storage call reports an error and the node must not acknowledge that append as durable. Complete records from an ambiguous failed batch may be present after restart and are reconciled by OpenRaft as uncommitted log state. The implementation must not retry against an uncertain in-memory/durable tail without recovery or a proven repair step.
- Vote and committed-index state becomes visible in memory only after its atomic control-state replacement completes. An ambiguous replacement error is returned as a storage error; recovery accepts only a complete validated prior or candidate control record and never guesses from directory order or timestamps.
- Truncation first durably publishes the logical suffix boundary and a new append generation, then removes or invalidates the obsolete suffix. Recovery ignores stale suffix records after a crash and finishes cleanup before allowing writes. Cleanup can remove complete suffix segments and may rewrite at most the one bounded segment that crosses the truncation boundary; it must not rewrite the retained prefix. Segment removals are directory-synced before cleanup is reported complete.
- Purge first durably advances `last_purged_log_id`, then reclaims wholly obsolete segments and syncs the directory. Recovery treats the persisted floor as authoritative and retries incomplete physical cleanup before serving. A segment straddling the purge floor may remain intact until all its entries are purge-eligible, bounding stale physical bytes to at most one segment target plus one oversized entry.
- Startup validates artifact identity/version, record checksums, index continuity, purge/truncate boundaries, and that the committed ID agrees with the retained or purged range under the current recovery rules. It reconstructs the in-memory reader index by scanning retained segments. This first slice does not promise startup time independent of retained history.

### Artifact and snapshot boundary

The segment family and control-state record are one version-3 Raft-log artifact. Versions 1 and 2 are unsupported: validation and open fail clearly without modifying the old artifact, creating a segment family, or treating the store as empty. No older reader, writer, or converter is retained for pre-release artifact compatibility. This envelope rejection prevents old commands from reaching the current command deserializer, including old `ConfigureConsumer` records without `retry_delay_ms` and `Command::Publish` payloads serialized as JSON integer arrays. The current command encoding uses compact text/base64 JSON so a maximum 64 MiB public payload fits below the 96 MiB peer-frame ceiling. The state-machine journal is also version 3, rejects versions 1 and 2 before command decoding, and caps each length-prefixed record at 96 MiB. The checkpoint, snapshot, group metadata, and broker-message retention remain separate artifacts with their own versions and ownership. The project-wide pre-release policy does not require older same-engine artifact versions to be readable or converted; it supersedes ADR 0037's general side-by-side promise for that case and makes no release-upgrade guarantee. Snapshot creation and installation do not authorize deleting Raft records; only OpenRaft's durable purge boundary does. A future cross-engine migration is a separately accepted product outcome, not a release-upgrade guarantee.

## Alternatives and tradeoffs

| Alternative | Assessment for Runnel |
| --- | --- |
| Keep rewriting the retained JSON map | Simplest current artifact and recovery path, but the measured serialized bytes grow with retained encoded history on append and control updates. This does not meet the selected persistent-work bound. |
| Segmented append-only entry records plus fixed control state | **Selected.** It keeps the OpenRaft append/flush boundary explicit, writes new entry bytes once, makes vote/commit updates independent of log length, and lets purge reclaim complete immutable segments. It avoids a new storage engine dependency. Runnel owns framing, truncation, directory ordering, crash recovery, and conversion tests; startup still scans retained entries, and sync latency remains device-dependent. |
| SQLite WAL-backed indexed table | Mature transaction and recovery implementation, with WAL durability selected through `synchronous=FULL`; WAL checkpointing later copies frames back into the database and introduces checkpoint behavior to measure and operate. It adds a database artifact and conversion boundary while Runnel must still map OpenRaft's callback, contiguous indexes, truncate, purge, and vote ordering to transactions. The official [WAL](https://sqlite.org/wal.html) and [`synchronous`](https://sqlite.org/pragma.html#pragma_synchronous) contracts describe these costs and durability modes. |
| RocksDB/LSM-backed indexed table | Provides checksummed WAL, indexed reads, write batches, and recovery, but introduces flush/compaction and MANIFEST behavior whose write amplification and tail cost must be measured. It is broader than this first fix and adds a new native storage dependency and artifact migration. See RocksDB's [WAL](https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-%28WAL%29), [WAL performance](https://github.com/facebook/rocksdb/wiki/WAL-Performance), and [MANIFEST](https://github.com/facebook/rocksdb/wiki/MANIFEST) contracts. |

Kafka's [log implementation](https://kafka.apache.org/43/implementation/log/) is a relevant primary example of append-to-active-segment, rolling, indexed reads, and segment-granular deletion. It also performs recovery validation and has its own protocol, replication, and retention guarantees; Runnel adopts none of those guarantees wholesale. The [Aether logging study](https://www.vldb.org/pvldb/vol3/R61.pdf) and Runnel's [systems-performance assessment](../research/systems-performance-research.md#replicated-logs-and-payload-movement-inspect-cross-layer-writes-before-redesigning-locks) reinforce that append bytes, barriers, lock time, compaction, and end-to-end tails are separate costs. The 2026 [XLL cross-layer logging study](https://www.usenix.org/conference/nsdi26/presentation/shawger) is relevant to duplicated payload persistence, but sharing payload records with the state-machine journal changes recovery and reference lifetimes; that remains a separate unaccepted design question.

## Implementation acceptance matrix

| Area | Required evidence |
| --- | --- |
| Persistent-work bound | At equal appended batch bytes and sync semantics, retained-history growth does not increase bytes serialized or submitted for append or committed-index persistence. Vary retained entries, entry payload size, and append batch size; report control bytes separately from entry bytes. This proves application-level submission, not device write amplification. |
| Append, vote, and commit ordering | OpenRaft storage contract tests plus focused tests prove contiguous indexes, the exact callback durability boundary, readable-on-return entries, serialized vote/log I/O, durable vote recovery, durable commit recovery, and validation of committed IDs against retained or purged history. |
| Interruption and corruption | Inject short writes, failed syncs, interrupted batch markers, torn final frames, invalid checksums, missing/duplicated segments, and control-file rename/sync failures. Reopen either reconstructs the complete valid prefix under the documented ambiguity rules or fails closed; it never acknowledges data whose append callback did not succeed. |
| Truncation and purge | Crash/reopen before and after logical-boundary persistence and during segment removal. Prove truncation cannot resurrect a superseded suffix, purge cannot expose entries at/below the floor, cleanup is idempotent, and partial-segment physical slack stays within the documented bound. |
| Snapshots and followers | Real three-process tests cover snapshot creation, purge, follower restart and replay, leader change, replication after recovery, and continued client publish/consume/ack. Existing state-machine journal and snapshot artifacts retain their current read/write behavior. |
| Format boundary | Version-1 and version-2 Raft-log fixtures are rejected unchanged; absent artifacts initialize v3; incomplete initialization or an unselected segment family fails closed instead of appearing empty. Journal versions 1 and 2 are likewise refused before command decoding; current records are bounded at 96 MiB. No pre-release conversion or mixed-version service is supported. A separately approved cross-engine migration needs its own source/target validation and activation contract. |
| End-to-end cost | Controlled repeated comparisons use the same topology, durability, payloads, batches, CPU/memory/storage limits, and snapshot/purge cycle. Report bytes serialized, bytes offered/completed by writers, file footprint, separately attributable filesystem/device totals when valid, throughput, p50/p99/p99.9, CPU, memory, and restart/follower recovery time. Establish the supported workload envelope; do not claim a latency or throughput improvement from the isolated rewrite-byte result alone. |

## Explicitly out of scope

This decision does not change public protocol behavior, quorum or acknowledgement semantics, commit batching, the OpenRaft version, broker-message retention, snapshot contents, state-machine journal layout, cross-layer payload ownership, storage resource limits, or a supported maximum log size. A later measured need may justify checkpointed indexes, a different storage engine, background cleanup scheduling, or cross-layer payload references, each with its own evidence and recovery review.
