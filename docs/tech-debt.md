# Technical debt register

This register records known implementation and documentation shortcomings. Product gaps belong in [backlog.md](backlog.md); an entry may link to the backlog item that will retire it. Entries are an inventory, not a priority order. Select work using current goals, dependencies, risk, and learning value. Keep remaining implementation work distinct from missing verification, and do not erase a useful partial improvement because the broader retirement gate remains open. Remove entries when the shortcoming is retired, and do not reuse their identifiers.

## TD-002: One file and a startup scan per local stream

- Status: open
- Impact: startup scans each complete stream file, older replay and candidate selection may require a linear scan, and retention cannot reclaim immutable regions independently. Record-location caches are bounded, but the request-identity map grows with distinct retained identities; bounded location indexing is not a bound on all retained metadata.
- Context: the one-file representation is intentionally the smallest durable log that can be tested end to end. The local engine keeps the newest 1,024 record locations and up to 1,024 sparse checkpoints, using the nearest available checkpoint for cold reads. Reads older than the sparse window can still scan from byte zero, and the request-identity map remains proportional to distinct retained request IDs. On baseline `d7c390a`, the targeted Criterion reopen benchmark reported 45.5 µs, 475 µs, 2.37 ms, and 9.59 ms for 100, 1,000, 5,000, and 20,000 default-format records with 100-byte payloads; reopen plus a cold poll reported 27.9 ms and 64.2 ms at 65,537 and 131,072 records. These are host-specific growth evidence, not product SLOs: they do not measure memory, retention, cleanup, large payloads, or storage amplification. The accepted [time replay selector](decisions/0038-timestamp-based-replay-selector.md) and its [derived index contract](decisions/0042-recoverable-replay-time-index.md) require lowest-offset lookup across regressing timestamps. The selected local index adds one prefix-maximum summary and byte cursor per 256 retained records; it rebuilds during the existing startup scan, but its memory, startup, and foreground costs remain unmeasured. See the [TD-002 scalability evidence note](design/td-002-storage-scalability-evidence.md) and [replay design](design/replay-sessions.md).
- Retirement condition: segmented, indexed storage with explicit format/version metadata, retention tests, and recovery benchmarks.

## TD-003: Protocol interoperability and secure client configuration

- Status: partially addressed; negotiated v2 framing, client/server behavior, local-engine TLS/auth startup, and process-level security cases are implemented. A generated Python client has verified the core independent interoperability flow; CLI security configuration remains open.
- Impact: the former JSON-lines path has been removed from the application protocol. V2 uses typed Protobuf envelopes and raw payload bytes, and local-engine startup now loads TLS and credential policy before binding. `runnelctl` cannot yet configure trust roots or bearer credentials, the Raft engine rejects application security until replica policy consistency exists, and the HTTP operations surface remains outside the contract. No compatibility with prior Runnel protocols or releases is promised.
- Context: [ADR 0031](decisions/0031-protocol-v2-contract.md) accepts v2 framing, schema evolution within a major, directional bounds, and explicit outcomes; [ADR 0035](decisions/0035-first-application-client-security.md) accepts the first TLS and bearer-role behavior. The implementation supplies the generated schema, exact preface and Hello/auth flow, bounded v2 application envelopes, safe client TLS/token configuration, exclusive custom trust roots, server policy/verifier and authorization modules, pre-mutation local/clustered delivery-response size checks, fail-closed local-engine startup/bind validation, and real-process coverage for authentication, authorization, startup, and batch response admission. Focused security and response-size process tests pass, as does the 132-test Raft library suite. A separately generated Python Protobuf 7.36.2 client has negotiated v2 with a real local server and completed stream creation, arbitrary-binary publish/poll, and acknowledgement for a 128 KiB payload. That one-off check verifies only the exercised flow; broader schema, TLS, and authentication interoperability should be verified when another language client or a materially changed wire contract makes that claim relevant. This does not create a cross-release support window.
- Retirement condition: expose safe runtime trust and credential configuration in `runnelctl` and pass the focused real-process protocol and security gates on the final head. Verify independent-client flows when adding another language client or making a material wire-contract change; do not require this check in routine CI. Keep HTTP operations security tracked separately and do not require a v1 fallback or a prior-release compatibility window.

## TD-005: Durability and delivery policies are hard-coded

- Status: partially addressed; retention semantics are accepted, while policy controls and runtime behavior remain open
- Impact: local durable writes, clustered quorum writes, broker-wide acknowledgement timeout and attempt-limit settings, and bounded protocol admission/storage execution are useful defaults, but they are different policy axes rather than one selectable contract. Retention now has a documented semantic contract, but the broker does not implement or expose configured retention or a storage-capacity/backpressure budget; documented durability modes and consumer-scoped retry policy are also absent.
- Context: [ADR 0036](decisions/0036-retained-history-and-disk-pressure-contract.md) accepts unlimited history by default, explicit finite age/size eligibility targets, durable-consumer and active-delivery protection, replay behavior below the retained floor, and separation of logical retention from physical write admission. It also defines the consequences of an explicitly configured zero-age or zero-size target and ties request-ID lifetime to logical record retention. This is a semantic decision only: neither engine performs retention cleanup or enforces physical capacity, and capacity inspectability, reserve policy, metrics, and runtime failure behavior remain open. The current implementation intentionally chooses conservative paths while other semantics are being established: local stream appends call `sync_data`, local consumer events call `sync_all`, clustered commands cross replicated log and state-machine journal boundaries, the acknowledgement timeout doubles as the initial redelivery delay, and an optional broker-wide attempt limit controls derived dead-letter movement. Protocol admission rejects connection/request saturation while local storage queues bounded work and reports `WouldBlock`; neither reserves disk capacity. The [durability and delivery policy boundary](design/durability-delivery-policy.md) records the observed behavior, separates these concerns, and defines evidence gates without prescribing an API or storage layout.
- Retirement condition: each public policy axis has an implemented, inspectable guarantee and outcome model, bounded-resource behavior, migration/compatibility consequences, and focused restart, failure, and resource tests for local and clustered paths where applicable. Retention's accepted semantic decision in ADR 0036 does not retire these configuration, capacity-enforcement, operational-inspection, and runtime-evidence gates.

## TD-006: Operational telemetry remains incomplete

- Status: open
- Impact: current metrics expose process uptime, request rates and latency buckets, connections, traffic bytes, publish/delivery/acknowledgement totals, in-flight deliveries, redelivery, dead letters, storage bytes, configured admission limits, admission rejection counters, health failures, snapshot and peer-transport activity, and bounded replication progress. Replication progress reports the maximum sampled Raft log-entry lag by numeric peer ID across groups led by the scraping broker, with explicit sample coverage; it is not message or byte lag, and full group coverage is not guaranteed above the 256-group bound. Metrics still cannot explain consumer lag, retained and reclaimable storage, queue saturation, broader cluster health, or resource pressure under load.
- Context: the metrics endpoint now covers the basic broker and transport path, reports the shared engine's currently tracked in-flight deliveries for both local and clustered delivery, exposes the configured admission boundaries and their rejection counters, and keeps a label-free process-uptime signal available when bounded engine health is unavailable. Cluster replication progress samples the metadata group and up to 255 data groups per scrape, rotating through data groups, and omits peer-lag samples when no sampled group is locally led. Real-server tests cover in-flight saturation, slow readers, slow-writer recovery, uptime progression, and scrapeability during a health stall; a three-process test now covers cluster replication progress and its unavailable behavior. An opt-in Rust timing feature and clustered profiling workflow provide deeper investigation data without adding timing calls to the default build, but those timings are not deployment-grade latency metrics. [ADR 0041](decisions/0041-first-consumer-lag-observation.md) now accepts a first exact-identity operator diagnostic over authenticated negotiated v2, with bounded local reads and a leader-authoritative clustered revision. This is a design contract only: the v2 security runtime, bounded diagnostic reader, barrier-backed adapter, and all lag output remain unimplemented. Aggregates, per-identity metric labels, age, and byte lag remain deferred; TD-006 stays open.
- Retirement condition: the deployment-grade operations backlog item is implemented and its metrics are exercised by integration or benchmark tests.

## TD-007: Storage conversion and artifact compatibility remain open

- Status: partially addressed; ADR 0037 accepts the first conversion and rollback contract, while runtime conversion and per-artifact compatibility evidence remain open
- Impact: the current Raft/state-machine files require their exact supported schema versions, and the new metadata/data-group directory layout has no migration path from the earlier single-group clustered layout. Long-lived rolling upgrades and in-place layout changes are not supported.
- Context: startup validates existing clustered logs, checkpoints, journals, snapshots, manifests, identities, and unsupported layouts before opening groups and fails closed without mutating unsupported state. Current state-machine checkpoints, snapshots, and journals require their exact schemas; earlier state-machine formats fail closed. Empty-directory startup still intentionally creates the directory and `storage.json`; that initialization is not migration. [ADR 0037](decisions/0037-offline-side-by-side-storage-upgrades.md) accepts an offline side-by-side conversion contract with explicit activation, a durable pending/commit boundary for the first target-only mutation, and source rollback only before target state is accepted. The [TD-007 storage compatibility evidence note](design/td-007-storage-compatibility-evidence.md) remains the record of local-stream read-forward fixtures, state-machine refusal tests, and runtime evidence gaps; no conversion command, selector, migration fence, rolling-upgrade promise, or downgrade implementation exists.
- Retirement condition: each supported artifact/layout has a declared read/write/mixed/migrate boundary and representative compatibility fixtures; an implemented bounded side-by-side conversion preserves all logical state; interruption, activation, write-pending resolution, rollback, stale-writer fencing, and real-process recovery tests satisfy ADR 0037; and unsupported layouts and old binaries fail closed. Rolling mixed-version conversion remains outside the accepted first path.

## TD-008: Distributed Raft backend is an early static-cluster implementation

- Status: open
- Impact: `runnel-raft` supports versioned local persistence, group-addressed framed TCP peer RPCs, a metadata group, one static data group per stream, reconciled stream activation, topology-free forwarding, stable stream metadata, durable publish request deduplication, preserved-state follower restart, leader failure, snapshot transfer with retry from byte zero, and snapshot lifecycle telemetry. Empty-replica recovery is test-only under [ADR 0018](decisions/0018-safe-replica-recovery-boundary.md). Static peer mutual TLS now authenticates configured cluster members, but the backend still lacks a supported empty-replica replacement lifecycle, dynamic membership, scalable placement and balancing, efficient large-stream representation, final fencing policy, repeated-interruption cost controls, automated credential rotation, a measured bound for deserialized peer object graphs, and production-grade operational policy. Replicating every stream to the same static voters is a useful three-node baseline but is not a scalable placement model.
- Context: the first process-level backend establishes a correctness baseline without committing the public model to Raft topology. All first-version groups use the same static voters, and shared-consumer ownership is replicated within each stream data group even though placement and policy remain simple. The [TD-008 static-cluster evidence note](design/td-008-static-cluster-evidence.md) records the current guarantees and separate membership, placement, and replacement retirement gates; the three-node smoke path remains development evidence rather than a production-cluster claim.
- Retirement condition: the distributed-engine backlog outcomes are complete, including topology-free access from any node, replicated metadata, failure and upgrade policy, credential lifecycle operations, decoded peer-memory bounds, observability, and documented production guarantees.

## TD-009: Snapshots rewrite the complete materialized group state

- Status: open
- Impact: snapshot creation and installation currently serialize or replace the complete retained state for a group. This keeps the first recovery path understandable, but snapshot cost grows with retained data and the default cadence is not yet tuned against realistic workloads.
- Context: the initial snapshot is deliberately independent from the compactable consensus log and is sufficient to recover a replacement replica without exposing storage details publicly. Snapshot and checkpoint serialization now uses borrowed retained-message views rather than cloning every message, with focused current-format retained-state recovery coverage; the complete materialized state is still serialized and replaced. A test-only checkpoint-persist error injected after checkpoint encoding but before atomic replacement confirms that the checked error leaves the running state, snapshot cache, and old checkpoint intact, while reopen selects the complete newer snapshot. This is state-machine recovery-selection evidence, not an actual checkpoint file-write failure, abrupt-crash, device-failure, or full OpenRaft log-store interaction guarantee. The current state-machine schema rejects pre-retry checkpoint and snapshot formats instead of reading them forward. Process metrics expose aggregate build progress and returned-attempt wall duration across registered Raft groups. The opt-in three-node probe ran two repetitions of four retained-state/payload cells under a 2-CPU, 2-GiB scope and confirmed successful builds; measured per-process mean build durations ranged from 6.4 ms to 1.345 s across the tested cells. Its 100-ms RSS observations are process-RSS lower bounds while a build was active, not peak or incremental snapshot memory; one short-build cell was only observed in one repetition. The 256-publish samples on a host with active desktop/browser load are descriptive, not stable latency evidence or a performance claim. Install cost, isolated lock wait, transfer retry waste, and peak memory remain unmeasured. The [TD-009 snapshot evidence note](design/td-009-snapshot-evidence.md) and [sample-level results](research/td-009-snapshot-build-hot-path.csv) record the run, current format boundary, staged install ordering, checked-error recovery result, 64 KiB chunking and retry-from-zero behavior, and remaining evidence gaps.
- Retirement condition: measured recovery and hot-path benchmarks justify a staged snapshot or extent-manifest design with bounded transfer work, compatibility tests, and no loss of retained messages or consumer progress.

## TD-010: Clustered state materializes complete retained history

- Status: open
- Impact: the clustered state machine keeps retained messages in materialized state and appends JSON journal records for committed apply entries. The journal avoids a complete state-file replacement on every apply, but serialization, copying, memory use, and recovery replay still grow with retained history.
- Context: the incremental journal and checkpoint path is the first durable step toward separating hot-path appends from materialized recovery state. Journal apply and replay now avoid redundant retained-payload clones and persist the journal batch before materializing in-memory state, while deliberately keeping the existing JSON checkpoint, snapshot, and journal formats. The current data-group state still owns every retained payload in a `Vec`, the journal and recovery parser materialize additional command representations, and full state images serialize retained history. The accepted [time replay selector](decisions/0038-timestamp-based-replay-selector.md) and [index contract](decisions/0042-recoverable-replay-time-index.md) require the minimum matching logical offset under timestamp regressions. The selected clustered index rebuilds from retained messages and is omitted from snapshots, but adds one prefix-maximum summary per 256 records; its memory, snapshot-install, rebuild, and foreground costs remain unmeasured. See the [replay design](design/replay-sessions.md) for its recovery and work gates. The [TD-010 retained-state evidence note](design/td-010-retained-state-evidence.md) records the current copy, scan, correctness, retention, and measurement boundaries without selecting a broader storage redesign.
- Retirement condition: retained-data growth, recovery, and resource benchmarks justify a durable representation whose append, read, and recovery work remains bounded without weakening ordering, replay, or acknowledgement guarantees.

## TD-011: End-to-end benchmark coverage is incomplete

- Status: open
- Goal: improve repeatable end-to-end benchmark coverage and comparable workload semantics.
- Rationale: repeatable measurements with explicit workload and durability semantics are necessary to identify regressions and compare results validly.
- Impact: the Criterion suite remains focused on local in-process paths. The end-to-end harness provides statistically screened same-host clustered comparisons and longer history runs, but it does not yet cover the complete fault, slow-consumer, batching, p99.9, or semantically equivalent competitor workload matrix.
- Context: microbenchmarks were added first to catch local regressions while the broker semantics and cluster recovery behavior were still changing. Containerized, clustered Runnel, retained-history restart/replay, peer-forwarding saturation, publish-batch, single-node native competitor, and first RF=3 competitor-publish measurements now exist, with scenario-scoped resource efficiency, aggregate/per-node CPU, resident-memory and storage-byte samples, p99.9 metadata where applicable, optional Linux profiles, and explicit semantic guardrails. Cluster probes now cover bootstrap-leader and non-bootstrap-follower process stop/restart sequences, and a sequential matrix runner preserves independent case artifacts across payload, batch-size, delay, concurrency, runtime, retained-history, and repetition dimensions. The opt-in batch-size expansion closes the repeatable matrix gap for the existing clustered publish-batch probe, but does not add consume batches or batch fault/recovery cases. An opt-in slow-consumer backpressure probe now verifies the current one-in-flight delivery window and duplicate-pull suppression while recording bounded latency and resource samples; it deliberately does not claim publisher throttling or rejection. Performance-sensitive pull requests use a same-host current-versus-main clustered comparison as their primary evidence and retain a single-node diagnostic; hosted daily runs provide the longer Runnel history, and competitor comparisons are kept in separate weekly/manual suites. Repeated summaries retain median, observed range, and relative range evidence; workload equivalence, complete tail-latency and fault coverage, publisher backpressure/rejection evidence, and stable optimization evidence remain incomplete. `cluster_retained_recovery` now declares its pre-restart-through-acknowledgement-and-client-close latency interval and enclosing resource-sample window; focused script coverage locks both boundaries. Earlier numeric recovery samples also include restart, replay, acknowledgement, and client close despite their former post-readiness label. The [TD-010 evidence note](design/td-010-retained-state-evidence.md) records the retained-state measurement limitations.
- Constraints: A future post-readiness measurement must use a separate scope and must not reinterpret existing end-to-end recovery samples.
- Retirement condition:
  - For TD-011 overall, the performance backlog outcomes provide repeatable machine-readable local, container, clustered, and comparable-broker measurements with explicit workload and durability semantics, plus enough repeated samples and profiling evidence to distinguish regressions from host noise.

## TD-012: Peer RPC connection strategy remains incomplete

- Status: open
- Impact: peer RPCs reuse connections, but ownership is split between persistent OpenRaft network clients and a `GroupManager`-scoped compatibility pool for forwarding, data-group setup, and stateless control requests. Each pooled peer has five bounded connections: one reserved for Raft control traffic and four shared by forwarding and setup traffic. Each transport is capped at 64 peer addresses, traffic beyond that cap uses manager-global bounded fallback capacity, and there is no multiplexing or cross-group pooling. Forwarding contention, direct aggregate connection growth as data-group count increases, overflow-address fairness, and end-to-end tail latency remain incompletely characterized.
- Context: the initial short-lived framed transport kept request boundaries easy to inspect. Reuse now covers append traffic, heartbeats, votes, snapshots, forwarding, and data-group setup, reserves control capacity, bounds idle-pool waits, lazily expires idle compatibility sockets, discards failed or timed-out connections, and has focused reuse, replacement, timeout, concurrency, and transport-lifecycle tests. The compatibility pool now closes with its owning engine. The pinned OpenRaft 0.9.25 call pattern uses separate network clients for replication and snapshot transfer and fresh clients for confirm-leader heartbeats and votes; replication-loop heartbeats share the replication client with append requests, while snapshots use a distinct TCP stream. The opt-in forwarding benchmark characterizes fixed-total-work follower-ingress publishing across bounded stream/data-group counts and records settled-boundary per-node established socket endpoint counts on Linux. A three-node container smoke now verifies this census using host-PID procfs where accessible and a bounded Docker-exec procfs fallback that confirms the exec UID matches broker PID 1. The successful diagnostic artifact records counts at both boundaries; its sample durations and limitations are detailed in the [TD-012 transport research note](research/td-012-peer-transport-ownership.md). These counts do not identify unique connections, Raft groups, or traffic classes; stable high-contention latency evidence and alternative-strategy comparisons remain incomplete.
- Retirement condition: transport benchmarks demonstrate whether connection reuse, multiplexing, or another bounded communication strategy improves throughput and p99/p99.9 latency without changing failure or fencing behavior.

## TD-013: Native competitor benchmark semantics are not equivalent

- Status: open
- Impact: the first comparison baseline uses Runnel's host-side protocol client, Kafka/Redpanda's native Kafka performance clients, and NATS's native JetStream benchmark client. Publish batching, consumer acknowledgement behavior, client startup, and latency visibility differ, so the numbers cannot yet support a definitive product ranking.
- Context: native tools provide an immediately reproducible single-node and RF=3 publish baseline while Runnel's public protocol and common benchmark client are still provisional. Results now record operation-specific acknowledgement, durability, replication, delivery, batching, client, latency, topology, and resource boundaries, reject inconsistent declarations, and mark mismatched comparisons as experimental and non-ranking. The three-node profile also adapts Runnel's existing static-cluster public-protocol publish probe; its host-side client is not subject to the competitor-client cgroup limits. The [TD-013 semantics note](research/td-013-native-competitor-semantics.md) records the comparison envelope and four candidate workload classes without making an implementation decision. A common equivalent workload client and fully comparable consume/recovery measurements remain absent.
- Retirement condition: a common workload client or rigorously equivalent adapters measure durable publish, consume with application acknowledgement, batching, recovery, resource usage, and tail latency across all supported brokers while preserving each broker's explicitly stated guarantee.

## TD-016: Initial shared dispatcher uses a simple scan and one delivery per member

- Status: open
- Impact: scalar grouped polling still returns one delivery per member, while consume-batch polling can hold a bounded active set of up to 1,024 records subject to a fully encoded response-byte limit. Local candidate lookup uses a bounded tail cache or scans retained storage from a sparse checkpoint; clustered selection traverses materialized records. Candidate work, key exclusion, and retained delivery state can still constrain throughput and scalability for large histories or highly concurrent worker pools.
- Context: the first implementation remains a semantic baseline for demand-driven delivery, not a target storage or scheduling architecture. Due-delivery polling uses a bounded deadline index, and local candidate lookup lower-bounds the committed offset in the ordered tail cache before checking acknowledgement and in-flight constraints; cold replay still scans from a sparse checkpoint. An alternating local Criterion comparison with 2,048 retained messages and a cursor at offset 1,900 measured lower poll/ack time in all three pairs (median paired reduction 5.78%, observed paired range 4.67–7.91%). This evidence covers one cache-resident workload; it does not establish an effect for cold replay or clustered candidate traversal. The held-delivery Criterion case sweeps 1, 4, 16, and 64 unkeyed members, with one message left unacknowledged per member; setup is outside the timed routine and per-iteration batching keeps one broker fixture live at a time. Existing acknowledged poll/ack cases cover two unkeyed members and four keyed members across four keys. A single 20-sample run on 2026-10-05 at revision `042a2add9bafee0f41bc50ecb6376fbe7a5f1238`, on an unscoped 12th Gen Intel Core i9-12900H with no Runnel or benchmark process but normal desktop activity, measured per-batch times of 20.322 µs (95% Criterion slope interval 20.043–20.583), 33.360 µs (33.102–33.694), 87.567 µs (86.942–88.281), and 338.067 µs (337.549–338.628), and per-message throughput estimates of 49.21k, 119.90k, 182.72k, and 189.31k messages/s at 1, 4, 16, and 64 members. Criterion reported one mild high outlier at one member and one severe high outlier at 16 members; there are no CPU or memory limits or across-run repeatability evidence. Treat this as one-run characterization only: it does not model simultaneous workers or establish clustered scalability. Consume-batch semantics now preserve same-key exclusion and one active set per member; performance and resource effects remain unmeasured. The stable-placement design records a possible future virtual-lane direction without changing the default scheduler.
- Retirement condition: representative workload evidence justifies further bounded scheduling or stable internal placement improvements while preserving batch and scalar ordering, backpressure, and stale-receipt fencing.

## TD-017: Dead-letter movement spans separate durable records

- Status: open; local target-write and source-event failure-boundary evidence is expanded, but the runtime retirement gates remain open
- Impact: new local moves use a stable source-stream/source-consumer/source-offset identity and do not append a second target record when a completed target append is retried or recovered. Legacy dead-letter records written before this identity was introduced remain opaque and cannot be retroactively reconciled by this slice.
- Context: local dead-letter movement still uses separate append-only stream logs and consumer checkpoints, but the target append uses the durable request-aware frame/index with an internal move identity and strict key/payload matching. The source acknowledgement remains after the target append or same-content reconciliation. Test-scoped failure injection now covers a partial target frame followed by restart/truncation and retry, a complete target frame reported as failed before its sync (the target is reconciled after restart), and a source acknowledgement event written before a synthetic sync error (recovery retries safely if needed). These tests verify eligibility and duplicate-safe recovery for the reproduced process-level file states; they do not reproduce actual device/filesystem sync failures or power loss. The real-process test `network_protocol_reconciles_dead_letter_after_ambiguous_poll_and_restart` drops the public poll response, restarts the server, reads and acknowledges the single moved message, then verifies the dead-letter consumer is empty. The clustered path already keeps the derived record and source progress in one replicated data-group transition.
- Retirement condition: a durable transaction or recovery reconciliation protocol provides duplicate-safe dead-letter movement while preserving bounded recovery and at-least-once guarantees. Corruption and retention behavior, actual filesystem/device failure and power-loss evidence, and legacy-record handling remain open; the item stays open until those runtime gates are implemented and verified.

## TD-018: Retry policy and dead-letter provenance are coarse

- Status: partially addressed; per-consumer timeout, attempt limits, and fixed retry delay are implemented
- Impact: applications cannot inspect source offset and attempt history from a dead-letter record, redrive safely, or choose richer terminal dispositions.
- Context: ADR 0027 adds durable configure/inspect operations, legacy broker-wide fallback, monotonic policy versions, and per-record policy pinning in local and clustered state. [ADR 0033](decisions/0033-fixed-consumer-retry-delay.md) adds `retry_delay_ms` from zero through seven days, pinned with the per-offset policy snapshot and kept separate from the acknowledgement lease. Both engines start a positive delay when a committed poll or stale acknowledgement first durably observes lease expiry, persisting `retry_not_before = observation_time + pinned_delay`; zero delay remains immediately eligible without a schedule row. Late observation starts a full positive delay, and no command means no expiry observation or progress. A deadline already persisted survives restart or leader transfer. If restart or transfer precedes durable expiry observation, the first later operation starts the delay in either engine. Focused local journal recovery and batch tests, clustered state-machine boundary and snapshot tests, and a real three-process leader-transfer test cover the accepted fixed-delay behavior. Clustered deadlines retain TD-020 clock risk; local persisted deadlines use wall time both before and after restart. Dead-letter provenance, redrive, and richer terminal dispositions remain open.
- Retirement condition: durable dead-letter provenance and redrive plus richer terminal dispositions are available and tested. Derived dead-letter targets remain consistent and non-recursive in both engines.

## TD-019: Delivery bookkeeping synchronizes durable state per delivery

- Status: open
- Impact: durable attempt and acknowledgement bookkeeping appends compact events and periodically checkpoints them instead of replacing the full consumer state file on every delivery. Scalar operations still cross one synchronous durability boundary per delivery; a consume batch records its assignment set or valid ack subset in one event and sync. Write and sync cost remains a throughput and tail-latency limit as concurrency and membership grow.
- Context: persisting attempts before returning messages makes retry behavior survive restart. The bounded append-only journal, replay, partial-tail recovery, compaction, active-state cache, stale-token fencing, and out-of-order acknowledgement coverage preserve those guarantees and produced an observed roughly 8% improvement in the focused benchmark; scalar deliveries still require their own durable write. Consume batches now reduce the local event count to one assignment or acknowledgement-subset event per operation, but their performance effect has not been measured. A core regression test replaces the acknowledgement journal with a directory after delivery, verifies append-open failure leaves the delivery eligible after restart, then confirms a later acknowledgement survives another restart. This covers a pre-append filesystem error, not a failure during a real device write or sync. The [delivery bookkeeping evidence note](design/td-019-delivery-bookkeeping.md) records the local event boundaries, clustered apply-batch distinction, known benchmark gaps, and outcome gates for a future group-commit experiment. A follow-up proposal to replace `sync_all` with `sync_data` for existing journal appends passed its replay checks but showed no repeatable improvement in controlled local comparisons, so closed PR #222 was not merged and does not change the debt status.
- Retirement condition: benchmarks show the implemented consume batches or a further bounded bookkeeping strategy materially reduce delivery overhead without losing durable retry state, acknowledgement safety, or predictable recovery. A narrower sync primitive alone is insufficient without a material improvement on relevant workloads and filesystems.

## TD-020: Clustered delivery leases use absolute wall-clock deadlines

- Status: open
- Impact: a leader chooses an absolute expiry timestamp and replicates it with each delivery. Clock jumps or skew between successive leaders can make redelivery materially earlier or later than the configured acknowledgement timeout; delivery tokens prevent a stale acknowledgement from committing, but they do not make lease timing predictable.
- Context: replicated absolute deadlines establish a simple failover baseline without adding a separate lease service. Deterministic tests cover forward jumps, fixed leader offsets, deadline boundaries, current-format restart and snapshot recovery, leader changes, no-command expiry, stale-token fencing, and the regression floor for a successor clock moving backward. Current checkpoints persist the lease-clock floor, and journal replay preserves its advancement and in-flight delivery across reopen; pre-retry checkpoint and snapshot schemas are unsupported. The state machine persists a per-group maximum command-time observation, so expiry evaluation cannot move below that already observed time after recovery or a leader change. The floor does not advance with elapsed real time: a deadline beyond it may still be delayed by a regressed clock, and no command means no lazy expiry evaluation. Inter-node offsets and forward jumps also remain unresolved; this is not a bound on real-time lease error. [ADR 0033](decisions/0033-fixed-consumer-retry-delay.md) accepts clustered positive retry delays starting at the first durable expiry observation, with the resulting deadline persisted in replicated state; zero-delay retries need no deadline row. Local positive-delay schedules use the same observation rule and persist an absolute not-before deadline, so wall-clock jumps before or after local restart can also make a retry early or late; the accepted contract does not add a local clock floor. The [TD-020 lease-time research note](research/td-020-lease-time-models.md) compares clock models and identifies the timing objective that remains open. Retry configuration and dead-letter provenance are tracked independently in TD-018, while retained delivery-state growth is covered by TD-010.
- Retirement condition: the supported clock assumptions and maximum timing error are documented and tested under leader changes, clock skew and jumps, local persisted-deadline restart, or delivery eligibility moves to a mechanism that does not depend on comparable wall clocks while preserving stale-delivery fencing and at-least-once behavior.

## TD-022: Local durable I/O has bounded async isolation but incomplete evidence

- Status: open
- Impact: local durable filesystem work is now dispatched through a bounded `StorageExecutor` on Tokio's blocking pool, and same-stream operations are queued behind a weakly tracked per-stream lane so they cannot consume all global storage slots. Storage pressure can still reject new work or inflate tail latency, and the remaining resource behavior needs dedicated slow-I/O evidence.
- Context: the first async boundary bound storage to 32 active and 32 queued operations with explicit `WouldBlock` admission, then centralized the boundary and added per-stream ordering and isolation. Focused tests cover ordering, cancellation, bounded admission, unrelated-stream progress, and storage-stall behavior, including bounded readiness failure and a scrapeable metrics fallback that omits unavailable engine samples. A real-process FIFO test holds one storage operation, fills its 32-entry same-stream waiter queue, verifies prompt excess-work rejection and failure metrics, and confirms unrelated durable traffic progresses and queued polls complete after release. A separate real-process test now blocks 32 distinct-stream storage reads in FIFOs, sends 64 candidate polls across distinct stream lanes, and observes exactly 32 prompt global-admission `storage_error` responses while 32 candidates remain admitted. At saturation, active requests report the 64-operation executor bound; protocol health fails promptly, readiness reports unavailable, and liveness plus the HTTP metrics fallback remain available with process/admission metrics and unavailable engine samples. Releasing the FIFOs lets all 64 admitted polls settle; health, readiness, metrics, and ordinary durable publish/poll traffic then recover. The per-stream test still demonstrates that `Broker::health()` can wait on the blocked stream mutex, while the global test demonstrates admission rejection before an additional storage health operation is admitted. These tests establish bounded behavior for synthetic FIFO reads and the tested queue boundary only; they do not model a slow or full device, establish fairness or global latency percentiles, or show shutdown behavior for an uninterruptible filesystem call. The [TD-022 storage-executor evidence note](design/td-022-storage-executor-evidence.md) records the exact executor/lane boundaries, distinguishes released FIFO-stall evidence from an uninterruptible filesystem call, and defines the remaining isolation, durable-outcome, tail-latency, and observability gates. On 2026-09-04, the real-process FIFO-stall tests `storage_stall_is_bounded_and_durable_traffic_continues` and `storage_stall_shutdown_is_bounded_and_restart_recovers` passed in five serial repetitions (10 test cases) with a 500 ms request timeout, `<1 s` stalled-request bounds, `<2 s` readiness/metrics bounds, `<2 s` shutdown bound after releasing the FIFO, and restart recovery; each case used a unique temporary data directory and ephemeral listener ports. The timed-out same-stream waiter recovery test, prompt persistent-connection shutdown test, and `just isolated smoke` also passed. The repeated stall pair took 5.67–5.76 s per test run after compilation. These are bounded pass measurements rather than per-request latency samples: p99/p99.9 tail data, fixed CPU/memory-scoped slow-I/O measurements, and shutdown evidence for an actually uninterruptible filesystem call remain incomplete, so this debt stays open.
- Retirement condition: measured storage execution boundaries keep filesystem stalls from starving unrelated network, health, and shutdown work while preserving per-stream ordering, durable acknowledgement semantics, bounded queues, and useful backpressure.

## TD-023: External protocol admission remains incomplete

- Status: open
- Response frame size is now configurable up to the protocol's 65 MiB default, can be lowered to 1 KiB, and is negotiated per connection with its configured value exposed as a metric.
- Impact: the server now bounds connection count, request frame size, in-flight request work, and request duration, with explicit rejection responses and metrics. Real-process coverage now exercises connection floods, oversized requests, in-flight saturation, slow writers, incomplete slow readers, served persistent connections with partial frames during shutdown, sustained in-flight recovery, and scrapeable metrics during a stalled storage health dependency. A per-stream FIFO test repeats saturation and release on the same live server and stream lane; a distinct-stream FIFO test also exercises the global storage-executor admission bound, prompt overload responses, observability, and recovery. Sustained device-level storage pressure and the full sustained resource-pressure matrix remain incomplete.
- Context: the negotiated v2 application protocol bounds preface, Hello, request, and response frames and negotiates directional limits; configured TLS/authentication also performs a handshake and bounded authentication exchange. The admission layer exposes configured limits and resource-specific rejection counters, uses bounded frame reads, connection/request permits, and request deadlines, and retains graceful drain behavior for already-used connections. These per-process controls do not bound total process memory or sustained slow/full-device behavior. Shutdown cancels frame reads for both new and already-served persistent connections, so a partial follow-up frame cannot retain a connection slot until its request deadline. Focused tests demonstrate that slow or malformed clients do not consume unrelated request capacity, and sustained pressure verifies active-work, rejection, saturation, timeout, and response-write-timeout metrics across recovery. FIFO storage probes now confirm that a bounded `200` metrics fallback retains process and admission samples, signals unavailable engine health, restores health and readiness after recovery, and prevents a timed-out same-stream waiter from poisoning the next durable request after release. A second per-stream FIFO episode now checks another bounded rejection and health/readiness/metrics recovery transition on the same live server, followed by a durable publish and poll. The separate `global_storage_admission_is_bounded_observable_and_recovers` real-process test blocks 32 distinct-stream reads in synthetic FIFOs, admits 32 more operations to the global executor queue, and promptly returns `storage_error` for 32 excess polls. During saturation, its scrapeable metrics retain process/admission samples and mark engine-health data unavailable; readiness returns unavailable while liveness remains healthy. Releasing the FIFOs lets all 64 admitted polls complete, restores health and readiness, and permits durable publish/poll traffic. This is finite synthetic FIFO evidence at the tested queue boundary: it does not establish behavior under slow or full devices, bound memory consumption, demonstrate a sustained resource-pressure matrix, establish operational-resource limits, or prove cross-version interoperability. The [protocol compatibility design](design/protocol-compatibility.md) records the proposed separation between these concerns.
- Retirement condition: the overload backlog outcome establishes configurable safe defaults and tests for connection count, request and response sizes, request duration, in-flight work, slow readers and writers, and rejection metrics without weakening graceful shutdown or normal client ergonomics.

## TD-025: Shared engine errors expose implementation-specific failure details

- Status: partially addressed; semantic engine outcomes and the v2 public outcome/stage contract are accepted, while wire implementation and evidence remain open
- Goal: make engine failures express messaging outcomes independently of storage representation and cluster topology.
- Impact: `runnel-engine::BrokerError` still retains concrete `io::Error`, `serde_json::Error`, poisoned-lock, leader-hint, and free-form cluster variants for diagnosis. The engine exposes backend-independent kind/outcome, while current v1 still has no authoritative wire outcome or stage; timeout, response loss, and post-proposal ambiguity remain client-side conservative classifications.
- Context: [ADR 0026](decisions/0026-semantic-engine-error-classification.md) accepts the engine-level boundary. [ADR 0031](decisions/0031-protocol-v2-contract.md) now accepts the v2 outcome and topology-neutral stage vocabulary, including the requirement that retryable carries proof of no effect, even after engine entry, and unknown is preserved whenever effect is uncertain. Existing engine assertions and real-server timeout/response-loss tests cover current behavior only; they do not prove v2 wire equivalence across local and clustered engines.
- Constraints: preserve confirmed rejection versus unknown outcome, stale-delivery behavior, and useful diagnostic causes. Keep topology and persistence details available internally without making them application obligations. Do not change current provisional v1 error behavior as though it were a compatibility promise; v2 implementation must carry the accepted outcome/stage explicitly.
- Retirement criteria: implement outcome/stage on every v2 application reply and pass real-process local and clustered tests for confirmed, definitive no-effect rejected, proved-no-effect retryable, and ambiguous unknown results, including response loss after durable apply, reconnect, and safe stable-publish-ID resolution. Documentation and compatibility fixtures must match that evidence; the engine-level portion remains complete under ADR 0026.

## TD-026: Raft log persistence and clustered cost bound

- Status: bounded v3 log-store runtime implemented; real-process recovery and supported-workload cost bound remain open under [ADR 0040](decisions/0040-bounded-raft-log-persistence.md)
- Goal: keep persistent work per Raft append and control-state update independent of older unpurged entries, while establishing the supported clustered cost envelope.
- Rationale: each durable Raft update should touch only new entries or bounded control state; the accepted persistence behavior removes history-sized rewrites, while workload-level costs still require measurement.
- Impact: the v3 `LogStore` appends only newly supplied entries to bounded segments and persists vote, committed ID, purge floor, and truncation state in bounded control data, rather than serializing the full retained map on every update. Recovery still scans and materializes retained entries, segment cleanup and sync latency remain, and the end-to-end clustered cost envelope has not been established. The former full-map implementation measured append plus committed-index pair latency rising from a 32.6 ms median with no retained entries to 75.8 ms at 4,096 entries, with serialized output growing from 8.8 KiB to 35.2 MB; for 100-byte entries, fixed sync latency dominated and measured growth was about 10%. Those historical results characterize the old local rewrite path, not v3 performance, end-to-end clustered commit latency, or device-level physical writes.
- Context: The v3 store uses checksummed append batches and fixed bounded control updates. Focused tests cover vote/commit recovery, contiguous appends, truncation and purge recovery, an incomplete final batch, completed-batch corruption, v1/v2 refusal without mutation (including old `ConfigureConsumer` and array-encoded publish command shapes), and separate opt-in append/control write attribution. The Raft command payload uses compact text/base64 JSON; the state-machine journal is version 3 and caps records at 96 MiB. Its bound test checks that maximum public payload expansion plus command metadata fits. Real-process follower/snapshot/purge interaction and injected write/sync/rename failures remain open. The [TD-026 persistence baseline](research/td-026-log-store-persistence-baseline.md) records measurements of the removed full-map path, live cluster runs through snapshot/purge cycles, the fixed-role opt-in counter boundary, and the controlled enabled/disabled diagnostic. The counters attribute application bytes offered and completed by `write_all`, fixed operation outcomes, and elapsed time for bounded serialization/write/sync/rename stages; failed `write_all` accepted prefixes are explicitly unknown. They exclude metadata/manifest writes and do not measure filesystem or device bytes. The opt-in log-growth probe captures per-process cumulative counters at publish/purge and restart/recovery boundaries; a restarted follower is marked as a new counter epoch. The final-source 2026-10-06 three-pair comparison completed on ext4 with 2 CPU/2 GiB limits. Median throughput was 12.936 msg/s disabled and 12.926 msg/s enabled; median p99 was 669.59 ms and 666.04 ms. This small comparison is inconclusive for counter overhead and is not a cost or performance bound. [ADR 0040](decisions/0040-bounded-raft-log-persistence.md) selects v3 append-only bounded segments and bounded durable control state. Versions 1 and 2 are unsupported and fail without mutation; this is a deliberate pre-release replacement with no release-upgrade compatibility promise. The [design contract](design/td-026-raft-log-persistence-contract.md) records the current crash/recovery invariants and remaining evidence. The [clustered commit-cost backlog outcome](backlog.md#keep-clustered-commit-cost-predictable-as-consensus-history-grows) and [systems performance research](research/systems-performance-research.md#replicated-logs-and-payload-movement-inspect-cross-layer-writes-before-redesigning-locks) retain the end-to-end measurement gates.
- Constraints: preserve OpenRaft append-flush ordering, vote and committed-index recovery, truncation, purge, snapshot recovery, and fail-closed v3 artifact validation. Unsupported v1/v2 artifacts must not be mutated or treated as empty. Keep consensus history distinct from retained broker messages; do not claim unbounded growth because snapshots and purge compact the retained log.
- Retirement condition: complete focused fault/recovery coverage and real-process follower/snapshot/purge tests for the current v3 format. A controlled clustered comparison across retained-log sizes and purge cycles must establish the supported workload cost envelope. Report serialized and application-submitted bytes separately from file footprint and any valid filesystem/device attribution, plus throughput, p50/p99/p99.9 latency, resources, and recovery cost. Do not claim a latency or throughput improvement unless stable authoritative results support it.

## TD-028: Aggregate local record materialization lacks a memory budget

- Status: partially addressed; per-record RNL3 fields are bounded, while aggregate recovery, indexing, and delivery memory remain unmeasured
- Goal: establish predictable memory use for local stream recovery, retained indexes, reads, response construction, and concurrent delivery.
- Rationale: the canonical RNL3 format limits keys to 128 bytes, payloads to 64 MiB, and identity strings to 1 KiB, but individual bounds do not cap aggregate broker memory.
- Impact: recovery retains up to 1,024 keyed record locations plus a bounded sparse index, while the request-identity map grows with distinct retained identities. Poll and replay materialize a payload up to 64 MiB; server response encoding creates additional buffers, and concurrent operations multiply those costs. No current measurement establishes a safe whole-process budget.
- Context: [ADR 0039](decisions/0039-rnl1-write-admission-and-legacy-read-compatibility.md) selects one RNL3 v2 frame for every local record and explicitly rejects old formats. The [local-format evidence](design/td-007-storage-compatibility-evidence.md#evidence-matrix) establishes bounded fields and current crash recovery. Historical RNL1 materialization concerns explain the earlier compatibility proposal, which ADR 0039 supersedes; old-format inspection and export are not supported recovery routes.
- Constraints: preserve checksums, offset continuity, incomplete-tail recovery, at-least-once delivery and acknowledgement behavior, public request-ID replay semantics, and bounded record parsing. Do not claim an aggregate memory or latency bound from per-field limits alone.
- Retirement criteria: account for recovery scratch space, retained indexes, identity maps, per-operation payload and response buffers, and concurrent operations; then use resource-scoped recovery, replay, and delivery workloads to demonstrate the resulting budget at supported concurrency. Keep focused tests for all accepted record boundaries, malformed frames, checksums, and crash-tail recovery.
