# ADR 0040: Bound Raft-log persistence work as retained history grows

- Status: accepted; implementation deferred
- Date: 2026-10-06
- Baseline: `f74a58d729cb5d8af5fa687221f1d98f02426937`
- Primary evidence class: design/research; secondary: correctness/recovery, performance
- Related: [TD-026](../tech-debt.md#td-026-raft-log-persistence-rewrites-retained-entries), [clustered commit-cost backlog](../backlog.md#keep-clustered-commit-cost-predictable-as-consensus-history-grows), [persistence contract](../design/td-026-raft-log-persistence-contract.md), [measured baseline](../research/td-026-log-store-persistence-baseline.md), [systems-performance research](../research/systems-performance-research.md#replicated-logs-and-payload-movement-inspect-cross-layer-writes-before-redesigning-locks), [OpenRaft 0.9.25 `RaftLogStorage`](https://docs.rs/openraft/0.9.25/openraft/storage/trait.RaftLogStorage.html), and [ADR 0037](0037-offline-side-by-side-storage-upgrades.md)

## Context

At this baseline, `runnel-raft::LogStore` keeps entries in a `BTreeMap`, then serializes and atomically replaces the complete retained map for append, vote, committed-index, truncate, and purge. The isolated TD-026 baseline found that a one-entry 1-KiB append plus committed-index persistence pair grew from 8.8 KiB serialized output and 32.6 ms median with no retained entries to 35.2 MB and 75.8 ms at 4,096 entries. The small-payload case showed fixed sync latency can dominate. This is direct evidence of a local rewrite mechanism and its growth; it is not a measurement of end-to-end quorum commit latency, physical device traffic, a supported workload limit, or a replacement design.

OpenRaft 0.9.25’s [`RaftLogStorage` contract](https://docs.rs/openraft/0.9.25/openraft/storage/trait.RaftLogStorage.html) requires log I/O to be serialized with vote I/O, a saved vote to be durable before return, entries to be readable when append returns, and the append flush callback to follow durable log persistence. The log must remain contiguous. Runnel also persists the committed ID and validates it on recovery. A replacement must preserve these boundaries and the current truncation, purge, follower replay, and snapshot behavior.

## Decision

Replace the full retained-map rewrite with a versioned Raft-log artifact composed of bounded, checksummed append-only entry segments and a fixed-size atomically replaced control-state record. Append persists only its supplied entries plus bounded framing and segment-roll metadata, then signals OpenRaft's flush callback after the required file and new-directory-entry syncs. Vote, committed ID, purge floor, and truncation generation/boundary are persisted in the fixed-size control state, whose serialized size does not grow with the retained log or update count. All writes for a Raft group remain serialized in one order.

Truncation and purge persist their logical boundary before segment cleanup. Recovery applies that durable boundary even if file deletion was interrupted and completes idempotent cleanup before writes resume. Complete segments are reclaimed as a unit; a partially covered segment may remain or be rewritten only within its fixed segment bound. Segment framing distinguishes an incomplete final append batch from a completed batch. Ambiguous storage failures return errors and are never treated as proof that no bytes or state reached disk; corruption within a completed batch or sealed segment fails closed.

Recovery continues to rebuild the retained log view and index from valid segments. This first slice bounds persistent work per append and control update with respect to prior retained entries; it does not claim startup time, in-memory indexing, fsync latency, device writes, or end-to-end commit latency are independent of history or hardware. It adds no group-commit delay and does not weaken the current durable callback boundary.

The artifact-level compatibility boundary in ADR 0037 applies: version 1 remains an immutable source during offline side-by-side conversion, the complete target is independently validated, and explicit activation selects it. Cluster conversion requires whole-cluster maintenance; source rollback closes after the first target-only durable mutation. The new Raft-log artifact does not absorb or change state-machine journals, checkpoints, snapshots, group metadata, or retained broker messages.

## Alternatives considered

- **Retain full JSON rewrites:** rejected because the measured serialized output grows with all retained entries on each append and control update.
- **SQLite WAL:** viable mature transactional storage, but `synchronous=FULL` still requires a durability sync and WAL checkpoints introduce page-copy work and another lifecycle. It adds a database artifact and conversion while Runnel still has to prove OpenRaft callback, contiguous-log, truncation, purge, and vote semantics. See the primary [SQLite WAL](https://sqlite.org/wal.html) and [`synchronous`](https://sqlite.org/pragma.html#pragma_synchronous) documentation.
- **RocksDB/LSM:** viable indexed storage with a WAL and batch writes, but flush, compaction, and MANIFEST work add write amplification and foreground-tail questions; a new native dependency and larger artifact boundary are disproportionate for the first slice. See RocksDB's primary [WAL](https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-%28WAL%29), [WAL performance](https://github.com/facebook/rocksdb/wiki/WAL-Performance), and [MANIFEST](https://github.com/facebook/rocksdb/wiki/MANIFEST) descriptions.
- **Segmented append-only log:** selected because the durable operation maps directly to OpenRaft's append/flush interface, prior entries need not be serialized or copied on append, and purge can reclaim immutable segments. Kafka's [log implementation](https://kafka.apache.org/43/implementation/log/) is a relevant primary design example for rolling append files and segment-granular cleanup, not a guarantee Runnel inherits.
- **Shared Raft/state-machine payload log:** not selected. [XLL](https://www.usenix.org/conference/nsdi26/presentation/shawger) reports a TiKV design that avoids duplicate payload persistence, but sharing ownership changes state-machine replay, deduplication, snapshotting, purge, and reference-lifetime invariants. First remove the independently evidenced full-map rewrite; evaluate payload sharing separately from controlled evidence.

The choice removes work proportional to prior retained bytes without requiring another storage engine. It accepts bespoke framing, recovery, truncation, purge, and conversion code, plus retained-history startup scanning. The [persistence contract](../design/td-026-raft-log-persistence-contract.md) records the detailed failure semantics, reference comparison, and implementation acceptance matrix.

## Consequences and implementation gates

The decision changes no current runtime behavior and makes no performance claim. Implementation requires focused storage fault/recovery tests and real-process clustered tests, with explicit coverage for append callback ordering, vote/commit recovery, truncation, purge, follower restart, snapshots, and the side-by-side artifact-upgrade boundary. A controlled same-semantics benchmark must show that serialized and application-submitted append/control bytes do not grow with older retained entries and must report end-to-end latency, resources, and recovery across retained lengths and purge cycles. The supported workload bound remains open until those measurements are stable and representative.
